前端项目通常会用 `index.ts` 集中导出模块能力。调用方的路径更整齐，但一个小功能的导入也可能牵连一个很大的导出入口。

SE-MBSE 对业务目录使用了 barrel 解析插件，将部分集中导入转换为直接导入。不过，查看当前封装后，值得讨论的首先是转换是否保留原有含义。

## 导入路径更短，不代表依赖范围更小

假设一个模块同时导出工具函数、页面组件和图形能力。调用者只需要一个工具函数，但开发工具仍可能需要分析入口关联的模块。

这不意味着所有 barrel 都应删除。公共入口也承担了封装职责：调用方不必知道内部目录如何组织。直接导入与集中导出，是分析成本和模块边界之间的取舍。

当前插件限定了一组业务目录，并先用快速检查判断源码里有没有相关 import，再交给底层插件处理，同时跳过 `node_modules`。限定范围的好处是，让变化保持在可以解释的区域里。

## 默认导入与命名导入不能混为一谈

封装代码里有一个很具体的兼容处理：把默认导入与命名导入混写的语句拆开。原因写在注释中——底层插件处理这一形式时会丢弃默认导入。

下面是简化示意：

```ts
// 转换前
import Editor, { createTool } from './editor';

// 先拆开，再由解析器处理命名导入
import Editor from './editor';
import { createTool } from './editor';
```

如果优化只保留 `createTool`，页面可能在某个运行路径才出现缺失。这样的错误不会因为冷启动变快而变得可以接受。

转换器的首要职责，是保证导出的绑定关系、副作用与执行含义没有被意外改变。

## 当前开关是显式选择

当前 Vite 配置要求开发模式并且 `USE_BARREL_RESOLUTION` 为 `true` 才启用这项业务目录优化。不能根据插件内的提示文字，误写成默认开启。

工程中还存在其他内部包解析器。测试模式会跳过这些内部包解析器，以保留包入口，让 `vi.mock` 能在预期边界生效。它与业务目录的 barrel 插件不是同一项开关，却说明了一个共同问题：改变解析路径，也可能改变测试隔离的位置。

## 如何判断优化值得保留

建议至少比较四种情况：

| 场景 | 检查重点 |
| --- | --- |
| 冷启动 | 相同缓存条件下的准备时间 |
| 修改公共入口 | 热更新是否到达正确调用方 |
| 混合导入 | 默认导入、别名与命名导入是否完整 |
| 测试运行 | mock 是否仍拦截预期模块 |

数据要来自同一份源码和相近环境。启动前是否清理缓存、是否已有依赖预处理结果，都应记录。一次很快的启动不能证明优化长期有效。

还要覆盖只有类型的导入、带注释的多行导入、入口副作用等样例。当前封装使用正则进行预处理，它适合有限输入约定，但不等同于完整的语法转换器。样例越来越复杂时，应考虑让语法树承担转换工作。

## 对团队更有价值的约束

构建优化最好拥有可关闭的开关、清楚的作用范围和一组回归样例。这样发生问题时，团队能够先隔离变量，而不是同时怀疑业务代码、构建缓存与插件。

同时，业务模块不要为了迁就优化器而随意暴露所有内部文件。可以让构建工具调整加载路径，但公共 API 的职责仍然需要维护。

barrel 优化适合解决已经定位到的分析成本问题。它的收益应由测量证明，语义正确则是不能交换的前提。
