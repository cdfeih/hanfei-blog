考虑这样一次建模请求：助手创建了一个元素及其图形呈现，数据库已经提交，但读取新图形时发生异常。调用方看到报错，于是再创建一次。

第一次其实已经成功，第二次又生成了一套对象。界面上可能只是多出一个方框，模型里却可能多出所有权、关系、表达式和图形引用。

AI 工具调用把这个传统问题放大了：模型很容易把“收到错误”理解为“刚才没有生效”，然后主动换参数再试。平台必须在回执中表达出更精确的事实。


## 1. 先把“成功”拆成几个问题

一次建模命令会经过参数检查、授权、前置条件验证、事务写入、派生处理、结果验证和回执保存。它们不一定一起成功。

| 问题 | 可以提供什么证据 | 不能由什么替代 |
| --- | --- | --- |
| 是否接受了命令 | 已保存的请求标识与操作记录 | 模型说“我开始了” |
| 是否提交了数据 | 物理事务完成状态 | 业务方法正常返回 |
| 是否达到建模目标 | 提交后读取的模型或呈现结果 | SQL 没抛异常 |
| 用户是否看到了变化 | 通知和刷新状态 | 数据已经提交 |
| 是否能够安全重试 | 原操作回执与实际模型核对 | HTTP 断开或通用报错 |

这几个维度混成一个 `success: false`，调用方就无法决定下一步。

当前 `ModelingResult` 因此保留 `status`、`semanticStatus`、`notificationStatus`，并携带 `operationId`、`requestId`、警告和具体结果。它们是恢复协议的一部分。

## 2. 幂等先解决“这是不是同一条命令”

SE-MBSE 使用调用凭证和 `requestId` 查找已有操作，再比较命令摘要：

```text
查找 (credentialId, requestId)
  ├─ 找到，摘要相同 → 返回已有回执，不再次执行
  ├─ 找到，摘要不同 → REQUEST_CONFLICT
  └─ 没找到         → 校验前置条件，登记新操作
```

同一个请求号不能代表“先创建 A，失败后再试创建 B”。否则请求号既是去重键，又成为任意覆盖旧命令的入口。

`digest()` 计算摘要时保留工具名称和命令内容，但移除 `approvalId`、`readToken`。这些字段是执行凭据或前置条件证明，不应仅因令牌刷新就把相同业务动作解释成另一条命令。

这不等于前置条件可以不检查。新命令进入执行前仍需验证；已有命令重放时，返回的是原操作事实，而不是借一个新 token 再执行一遍。

### 失败之后该复用哪个请求号

如果已保存 `FAILED_NO_COMMIT`，再用原请求号会得到原失败回执。修正业务原因后，要使用新的请求号。

这里区分了两种行为：

- **结果查询式重放**：我不知道上次结果，重复同一个请求，获取原记录；
- **修正后的新尝试**：我已经知道上次没提交，准备执行新的尝试。

把这两件事混在一起，会让服务端无法可靠去重。

登记操作时还需要处理并发竞争：两个相同请求可能都先查到“不存在”。实现捕获登记时的唯一键冲突，再读取已有操作并核对摘要。应用层的“先查再写”本身不足以消除这个窗口。

## 3. readToken 代表什么，比有没有 token 更重要

模型通常先读，再决定怎么写。读取与写入之间，用户可能修改工程，其他命令也可能改变模型。

最强硬的做法是任何写入都必须携带快照 token，但这也会增加操作链长度。当前实现允许两种路径。

### 快照路径：证明“我依据的状态仍然成立”

显式 `readToken` 会进入快照验证。创建、删除和一般更新采用相应验证逻辑，检查工作区、目标与引用等依赖。部分工具还会要求工程整体未发生变化。

即使系统允许不带 token，也不代表一个明确传入、已经过期的 token 可以被静默忽略。调用者既然声明依据某个快照，就应该接受它失效的结果。

### LIVE 路径：基于执行时的当前状态工作

未提供 token 且未启用强制 token 模式时，工具创建一个 `Purpose.LIVE` 票据。

它记录当前作用域中的依赖和代数信息，但没有历史快照摘要，也不冒称助手此前已经读取过这些内容。业务操作依然需要通过权限、可编辑性、引用和数据锁等校验。

这两个模式承担不同承诺：

| 模式 | 提供的承诺 | 不应作出的承诺 |
| --- | --- | --- |
| 显式快照 | 验证读取时的依赖是否仍有效 | 自动解决全部并发冲突 |
| LIVE | 在执行保护内按当前状态校验和操作 | 证明模型的旧推理仍然正确 |

例如“在当前包下添加一个指定名称的元素”，可能适合当前状态校验；“把我刚才审查过的那组关系全部替换掉”，通常更依赖先前快照。

选哪一种，不应只看能否少调用一次工具，而要看业务是否依赖之前观察到的状态。

## 4. 写入保护还要覆盖派生事件

`ModelingWriteGate` 在当前普通工程共享模式下维护进程内的工程级活动状态。它协调 MCP 命令和接入保护的人工操作，对冲突返回忙碌状态。

这里不能把它描述为分布式锁：这部分状态放在进程内结构中，跨实例的一致性需要另行评估。助手会话上的持久化租约解决的是另一个问题，也不能替代所有写入方之间的协调。

更细的一层是写入许可 `Permit`。建模命令可能触发派生事件，事件又在其他线程中继续修改模型。如果只允许父线程写，派生工作会被误拒绝；如果让派生线程等待父命令释放锁，父线程又在等待派生工作结束，就可能相互等待。

当前实现通过短生命周期许可绑定工作区与事件作用域，使派生工作携带同一次写入的资格继续执行。许可关闭时等待关联工作真正退出，不能在父方法刚返回时就失效。

这种设计将“谁有资格参与本次写入”和“哪个线程正在执行”分开了，但仍要保留工程、分支、版本一致性检查，防止许可被拿去写另一个作用域。

## 5. 物理提交之后，才验证最终结果

核心执行顺序可以压缩成下面这条链：

[![命令从幂等检查进入事务，提交后等待派生工作并验证结果，最后形成可恢复回执](/images/articles/mcp-write-lifecycle.svg)](/images/articles/mcp-write-lifecycle.svg)

手机阅读可点击图片查看大图。

`ModelingToolSupport` 在事务中注册完成回调，记录是否开始提交、最终是否提交。业务动作可以返回 `ModelingPostCommitResult`，其中一部分是即时结果，另一部分是提交后执行的验证函数。

简化后是：

```java
try (var scope = openPermit(workspace)) {
    result = transactions.execute(() -> {
        registerCommitCallbacks();
        return action.apply(input);
    });
    scope.awaitCompletion();
    result = verifyAfterCommitIfPresent(result);
}
```

这不是为了多读一次数据库，而是为了选择正确的观察时点。

本轮表达式工具调整中就出现过这样的问题：保存表达式后，马上通过索引查询回读，观察到的状态可能还没有反映本次物理提交。修正后的思路是先使用刚持久化的对象组织即时结果，再把需要验证最终语义的读取移到提交后。

图形创建也有类似问题。创建动作已经返回一个标识，不代表提交后一定能读到符合要求的呈现。验证函数可以检查最终呈现，并保留真正创建的对象标识，便于失败时核对。

但提交后验证有一条不可改变的事实：**验证失败不会让已经提交的数据自动回滚。**

## 6. 四种回执对应四种恢复策略

| `status` | 当前能证明的事实 | 调用方下一步 |
| --- | --- | --- |
| `SUCCEEDED` | 执行和相应验证正常结束 | 使用结果，按需要刷新界面 |
| `APPLIED_WITH_WARNINGS` | 操作已应用，但存在后续问题或部分结果需要核对 | 保留已创建标识，检查警告与语义状态 |
| `FAILED_NO_COMMIT` | 能证明这次没有提交 | 修正原因后发起新请求 |
| `UNKNOWN` | 现有证据不足以证明最终提交结果 | 查询原操作与实际模型，停止自动重做 |

其中最重要的是后两种不能混用。

当前实现会综合 `transactionEntered`、`commitStarted` 和完成回调结果判断异常。如果根本没进入事务，或者明确在提交开始前结束且未提交，可以归为未提交失败；如果物理提交边界已经不明确，就保守返回 `UNKNOWN`。

相反，如果已经确认提交，随后通知、派生工作或验证失败，就返回带警告的已应用结果，并尽可能保留实际结果和恢复提示。

### “有警告”并不总等于 MCP 工具错误

`ModelingResult.toolError()` 的实际判断是：

```java
return "FAILED_NO_COMMIT".equals(status)
    || "UNKNOWN".equals(status)
    || "PARTIAL".equals(semanticStatus)
    || "PARTIAL_OR_UNKNOWN".equals(semanticStatus);
```

一个已应用但需要刷新的结果，不该自动被归为“请换方法再做一次”。反过来，批次虽然有部分提交，如果语义结果只是部分完成，仍应明确让调用方感知未完成状态。

这解释了为什么回执既要有提交状态，也要有语义状态。它们服务于不同的判断。

## 7. 批量操作不是一个大事务

`apply_model_changes` 容易让调用者产生一种直觉：一个批次就是一次原子提交。

当前实现并非如此。各子命令独立执行事务，出现问题后停止继续执行，先前已提交的子命令不会因为后面的命令失败而自动撤销。

例如：

```text
命令 1：创建元素 A → 已提交
命令 2：设置 A 的属性 → 已提交
命令 3：建立关系 → 失败，未提交

最终：A 和属性仍然存在，关系未建立。
```

这里的批次提供顺序组织和结果聚合，不能宣传成“全有或全无”。实现也不支持靠本批次临时引用随意串联尚未解析的对象，更不能把通用撤销当作天然可用的补偿事务。

LIVE 模式允许命令在当前状态上处理重叠目标；显式快照路径则还有依赖冲突约束。调用方需要理解自己使用的是哪种前置条件，而不是把单命令的 token 原样堆进一个大数组。

需要原子性的复杂业务，应设计专门的领域命令，在受控事务边界里完成；需要长流程的任务，应接受部分完成，并设计逐步核对与补偿。

## 8. 回执保存失败也会形成不确定性

还有一个不显眼的故障窗口：模型已经修改，但最后保存操作结果失败。

如果这时仅返回普通系统异常，助手可能丢失恢复线索。当前实现会保留 `operationId` 并返回未知状态，指导调用者查原操作和真实模型。

同理，响应太大时也不能把操作标识截掉。压缩回执仍保留状态、请求号、操作号及 `get_model_operation` 查询指引；具体结果可以分段取回。

可见，回执不是最后随手拼装的展示对象，而是连接事务事实与下一次决策的持久协议。它需要和写入路径一起设计。

## 9. 我会如何验证这类工具

只测“调用成功返回成功”远远不够。真正决定恢复质量的是故障发生在哪里：

- 同请求重复发送，业务动作是否只执行一次；
- 同请求号换参数，是否被拒绝；
- 提交前失败，是否明确报告未提交；
- 提交结果不确定，是否避免自动执行第二次；
- 提交后回读失败，是否保留原对象标识；
- 通知失败，是否错误地暗示数据回滚；
- 最终日志保存失败，是否仍返回恢复入口。

这些场景在源码中的写入测试已有对应覆盖意图。本次文章工作没有重跑完整后端测试，也没有注入真实数据库故障，不能据此声称整套事务链已重新验证。

我另做了一个独立实验，直接编译固定提交中的 `ModelingResult` 和 `McpOperationReceipt`，验证错误分类与压缩回执保留字段。实验可在[配套目录](/examples/mcp-assistant-20261020/README.md)复现，它证明的是回执类的实际行为。

## 10. 这套设计换来了什么，又没有解决什么

它让助手能够区分“应该修正参数”“应该核对原结果”“可以继续下一步”，减少因笼统报错引发的重复写入。

代价也很具体：操作记录、摘要、快照、事务完成状态、派生工作和恢复查询需要共同维护。工具返回不再只有一个布尔值，前端和模型都需要理解更丰富的回执。

它没有提供分布式 exactly-once 保证，也没有把多命令流程变成可任意回滚的事务。`UNKNOWN` 正是承认这些边界的方式。

对工程平台来说，明确表达不知道的部分，比把每次异常都包装成“失败，请重试”更有用。用户可以接受一次需要核对的操作，很难接受系统在不确定时继续自动制造更多不确定结果。
