一个建模平台的前端，既要处理工程管理页面，也要驱动画布、工具栏和复杂属性面板。随着能力增长，把文件继续放进同一个 `common` 目录，很容易让基础组件与业务页面互相依赖。

拆包能够让这些依赖更容易看见。但目录有了边界，不代表代码已经解耦。观察 SE-MBSE 的前端工作区，可以把问题具体化为：什么需要一起协作，什么应该拥有独立的接口？

## 先区分能力，再划分包

当前工程的工作区包含 `pixichart`、`reactPixichart`、`ui`、`icons` 和 `utils` 等包。它们承担的职责并不相同：图形能力与 React 的连接有适配层，通用界面与业务应用也没有完全混在一起。

其中，`reactPixichart` 明确依赖工作区里的 `pixichart`；Vite 则将这些内部包解析到本地源码。这样修改包内实现时，可以直接在应用中观察效果。

下面是便于理解的职责示意，不是完整依赖图：

```text
业务应用：建模页面、项目管理、属性面板
    ↓ 使用组件或服务
React 适配、通用 UI、图标与工具
    ↓ 其中图形适配连接
图形能力包
    ↓
本地渲染引擎
```

这个划分的价值在于，讨论某个功能时可以先判断：它是产品规则、框架适配，还是图形基础能力。例如，画布选择框的几何计算可以属于图形能力；“某类工程是否允许编辑”的判断则需要业务上下文。

## 工作区成员与本地依赖是两回事

`pnpm-workspace.yaml` 纳入 `packages/*`，同时显式排除了 `packages/pixijs-source`。但图形包又通过本地文件依赖使用这份源码。

这说明“放在同一个目录树里”与“参加同一套工作区管理”并不等价。引擎源码有自己的包组织与构建需求，把它排除出工作区，不意味着它不存在，也不意味着生产环境改用另外一份引擎。

阅读工作区时，我会同时检查三个位置：

| 位置 | 要回答的问题 |
| --- | --- |
| 工作区配置 | 哪些包被统一管理？ |
| 包的依赖声明 | 哪些能力依赖哪些能力？ |
| 构建工具的 alias | 运行和构建时实际加载哪份代码？ |

只看其中一个文件，容易把“声明上依赖某个包”误解为“最终一定加载它的发布产物”。

## 统一 React 版本解决的是基础一致性

当前工作区对 `react` 和 `react-dom` 设置了 overrides，意图是让各包的版本解析保持一致。这是一条重要约束，但它不能替代运行时检查。

独立组件包是否正确声明 peer dependency、最终打包是否带入额外的 React、测试与应用是否使用同样的解析路径，仍然要分别确认。尤其当内部包既支持独立构建，又允许应用通过 alias 直连源码时，这两条路径可能暴露不同问题。

不要把“安装没有报错”当成依赖边界正确的证明。

## 源码联调之外，还需要产物验证

源码联调缩短了修改到反馈的距离，也可能遮住发布问题：源码可以访问的文件，没有被打进产物；本地 alias 能找到的入口，没有出现在包的导出声明中。

一个实用的验证办法是保留两条路径：日常开发从源码联调；准备交付时，在最小消费示例中只安装构建产物。后者验证入口、类型声明、样式和必要资源是否完整。

对于团队，包的维护责任也应随之明确：谁接受新增公共 API，谁判断某个接口只适合业务内部，谁负责兼容性变化。没有这些约定，公共包很快会成为新的大杂烩。

拆包最终应减少理解一个变化所需的知识范围。判断是否值得继续拆，可以看一次真实需求改动涉及多少职责、是否出现反向依赖，以及调用者能否仅凭接口完成工作。
