看到一个后端有许多 Maven 模块，又使用了 Dubbo，很容易直接把它称为微服务系统。但模块数量、调用框架和部署形态并不是同一个维度。

SE-MBSE 的后端把系统管理、项目建模、研发管理和外部适配分成多个模块，各业务域又区分 API 与实现。启动模块聚合服务实现，基础配置里采用 `injvm` 协议。这更适合从模块化单体的视角理解。

## 三种边界分别解决不同问题

API 模块表达对外契约，例如接口、DTO 和共享枚举；service 模块承载具体业务实现；web 模块负责组装可启动的应用。

用简化结构表示：

```text
启动与组装
    ├── 项目建模实现 → 项目建模契约
    ├── 系统管理实现 → 系统管理契约
    └── 外部适配实现 → 相关领域契约

公共技术设施由独立 core 模块提供
```

契约边界限制调用方需要知道的内容，实现边界方便组织业务代码，部署边界决定进程与运行环境。它们可以重合，也可以不同。

当前 POM 与基础配置能够证明模块的组装方式，但不能证明所有调用都已严格遵守 API 依赖，更不能据此断言任何环境都没有额外覆盖配置。

## 本地调用仍然需要维护契约

同进程调用省去了跨网络的一部分成本，却不会消除接口演进问题。一个领域向另一个领域返回数据库实体，调用方仍可能依赖实现细节；一个 DTO 变更，也仍可能使多个模块同时修改。

对于技术负责人，值得关注的指标是变化传播范围：修改一条业务规则，是否迫使无关模块改动？调用方能否只通过 API 理解结果？异常是否暴露了实现模块里的内部类型？

把这些问题解决好，模块边界才真正有用。

## core 不应成为绕过边界的通道

共享模块很容易被当作“双方都能访问”的中转站。某个业务对象被两个模块使用后，就直接放进 core，看起来消除了依赖冲突，实际上可能只是把业务耦合搬到了更底层。

当前项目规则明确区分公共技术设施与业务语义。可以据此审查新增代码：序列化、日志关联、通用锁接口属于技术机制；模型元素生命周期、项目权限决策则需要保留明确的领域归属。

如果无法判断某段逻辑归谁，先把输入、输出及决策责任写出来，通常比立即抽一个公共工具类更有效。

## 什么时候才值得拆成远程服务

部署拆分会引入超时、重试、消息顺序和数据一致性等新约束。模块内部可以直接依赖的一次调用，跨进程之后就需要重新定义失败含义。

因此，拆分前可以先检查：是否有独立扩缩容需求，是否需要独立发布，数据归属是否清楚，团队是否能独立维护服务，以及调用失败时上游如何降级。

如果边界本身尚不清楚，远程化通常不会自动修好它。反过来，API 与实现已经分离，也不意味着拆服务会毫无成本：进程内对象、事务和上下文仍可能需要重新设计。

## 用依赖检查支持团队协作

一个实用的做法是，把禁止依赖的方向写进构建或架构检查，并为跨模块接口准备契约样例。涉及多个团队成员的改动，先审 API 与兼容策略，再进入实现细节。

这样模块化的收益会落实到日常协作：谁负责哪条规则、哪个接口允许被依赖、一次变化如何分批交付，都有可检查的依据。

模块化单体可以是明确的架构选择。评价它时，应看职责是否清晰、变化是否可控和交付是否稳定，而不是以服务进程数量作为成熟度标准。
