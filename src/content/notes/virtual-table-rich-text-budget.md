需求表里的一个单元格，可能包含几段文字、一张图片、一个列表，甚至一张嵌套表格。表格还需要支持树形展开、自定义列、拖拽、编辑和属性面板联动。

在这样的界面里，“打开虚拟滚动”是优化的一步。真正决定体验的，还包括可见单元格做了多少工作，以及滚出视口以后，之前的计算有没有白做。

SE-MBSE 最近的需求表调整，给了我一个适合拆解的例子：展示层用轻量富文本预览，编辑时才打开编辑器；虚拟列表管理挂载范围；清洗结果通过有界缓存跨越组件的卸载周期。

本文讨论实现机制和可以验证的边界，没有一组完整应用的前后性能基准，因此不会给出“提速多少倍”的结论。

## 1. 先拆成本，才知道虚拟化解决了哪一部分

可以用一个粗略模型理解整张表的成本。它是分析工具，不是实测公式：

```text
首屏成本 ≈ 全量数据获取与处理
         + 首批可见行 × 列数 × 单元格工作量
         + 布局、绘制与图片解码

滚动成本 ≈ 新进入视口的行 × 列数 × 挂载工作量
         + 行高变化引发的布局工作
```

虚拟滚动主要减少同时挂载的行数。它不会自动把接口变成分页查询，也不会消除全量树过滤、展平、排序和表单同步。

当前需求表的请求仍获取列表，然后执行树范围与关键字过滤。因此，即使页面只显示几十行，数据层也可能处理整个集合。评审时需要把网络、数据变换和渲染分别测量，不能用 DOM 节点变少来证明全部成本已经受控。

对于富文本，单元格内部成本同样重要。每个可见格子都实例化编辑器，和只渲染一次清洗过的 HTML，是两种不同的生命周期。

## 2. 阅读路径与编辑路径分开承担责任

`requireTableDiagram.tsx` 在阅读状态使用 `RichTextPreview`。用户发起编辑时，才打开包含 `QuillEditor` 的弹窗。

预览组件的关键结构很短：

```tsx
// 源码节选，省略外层样式
const html = useMemo(
  () => (richText ? sanitizeRichText(richText) : ''),
  [richText]
)

return richText ? (
  <div className="ql-editor" dangerouslySetInnerHTML={{ __html: html }} />
) : (
  <div className="ql-editor">{text}</div>
)
```

这条阅读路径不创建编辑器、工具栏或编辑事件监听；纯文本后备分支交给 React 文本渲染。Quill 的样式用于还原列表、缩进、字号等表现。

拆开以后，也增加了新的责任：编辑器生成的内容，预览器能否正确表达？历史数据里的类名是否还识别？保存后预览与再次进入编辑是否一致？这些都需要用实际内容验证。

我会把“编辑后能保存”与“列表中能正确阅读”列成两个验收项，避免前者通过后掩盖展示兼容问题。

## 3. HTML 预览需要明确的内容策略

进入 `dangerouslySetInnerHTML` 的内容先经过 `sanitizeRichText`。实现创建独立 DOMPurify 实例，并配置允许的标签、属性和清洗 hook，避免把这套规则附加到应用其他清洗实例上。DOMPurify 官方提供实例与 hook 扩展能力。[DOMPurify 项目文档](https://github.com/cure53/DOMPurify)

这个项目的内容策略包含几层：

| 对象 | 本实现的处理 |
| --- | --- |
| 标签与属性 | 明确列出段落、列表、图片、表格等允许项 |
| 内联样式 | 保留颜色、字号、对齐等少量属性，丢弃其他属性 |
| CSS 值 | 进一步过滤 `url()`、`expression()`、`var()` 等形态 |
| class | 只保留识别到的 Quill 展示类 |
| 链接 | 添加 `rel="noopener noreferrer"` |
| 图片地址 | 规范化历史反斜杠路径，并限制地址形态与位图 data URL 类型 |

先限制 CSS 属性，再检查值，是因为“颜色”与“固定定位遮住整页”对阅读组件的意义不同。类名也需要控制，否则内容里的普通字符串可能意外匹配应用样式。

图片允许 HTTPS、部分其他地址形态和相对路径，但不允许 SVG data URL。这里仍有两条边界需要分清：

- HTML 清洗不等于外部资源来源控制。允许的远程图片仍可能发起请求；若产品需要限制资源域名，应另设资源策略。
- 清洗后内容可以很大。标签合法，不代表巨大图片、超长文本或深层表格的渲染成本合理。

此外，这个模块在初始化时使用 `window`，属于浏览器侧实现。若迁入服务端渲染环境，需要调整实例创建位置与 DOM 依赖，不能原样复用。

## 4. 为什么有了 useMemo，还需要跨组件缓存

`useMemo` 保存的是组件实例生命周期内的计算结果。虚拟行卸载之后，再滚回来通常会重新创建组件，原来的 memo 也就不在了。

`memo` 可以减少某些 props 未变化时的更新，但它同样不能让已经卸载的实例继续存在。

因此当前预览模块维护了一个以原始 HTML 为键、清洗结果为值的 Map：

```text
同一个组件再次渲染
  → useMemo 尽量复用

虚拟行卸载后重新挂载
  → 模块缓存尝试复用清洗结果

内容变化
  → 新 HTML 键，重新清洗
```

选择内容作键还有一个直接好处：两条记录内容完全相同时，可以共享结果；编辑一条记录以后，不会因为继续使用相同业务 ID 而读到旧 HTML。

代价是原始 HTML 自身也要常驻缓存。若只限制条目数，少量超长内容仍可能占据很大空间。

## 5. 缓存要同时约束条数与内容规模

源码设置了两个限制：

```ts
const MAX_CACHE_SIZE = 1_000_000
const MAX_CACHE_ENTRIES = 200

const size = html.length + sanitized.length
```

缓存命中时，先删再插，使该条目成为最近使用项；插入前持续移除最旧项，直到条目数与累计长度都符合限制。单条输入与输出合计超过预算时，仍返回清洗结果，但不放入缓存。

这里的 `length` 是 JavaScript 字符串长度口径，不能直接写成“缓存最多 1 MB 内存”。实际内存还包含字符串表示、Map 条目以及引擎开销。

一个简化例子能说明双限制的必要性：

```text
200 条很短的 HTML：
  容易先触发条目上限

20 条很长的 HTML：
  可能先触发累计长度上限

1 条特别长的 HTML：
  本次可以展示，但不长期占据缓存
```

缓存只减少重复清洗，没有减少 DOM 重建、布局和图片解码。特别长的内容不进缓存，来回滚动又会重新清洗；如果这类内容常见，应考虑摘要、折叠或按需查看完整内容等产品方案。

当前策略在模块生命周期内固定。如果以后支持动态切换清洗策略，缓存键必须包含策略版本，或在切换时清空。否则，同一段 HTML 可能继续命中旧规则的结果。这个问题在固定配置下不突出，却是把模块提升为通用组件时需要补齐的契约。

## 6. 虚拟表格的尺寸和 DOM 结构会影响交互

本次适配没有停在 `virtual={true}`。

`BuiltinTable` 使用 `ResizeObserver` 测量外层容器，计算表体宽高，并给虚拟模式传入数值形式的 `scroll.x`、`scroll.y`。这与 Ant Design 虚拟列表示例要求的数值滚动尺寸一致。[Ant Design Table 文档](https://ant.design/components/table/#components-table-demo-virtual-list)

当前高度计算减去了约 62px 的表头空间，最小传入值为 1。这个近似值是实现约束：将来改变密度、表头换行或主题尺寸时，应重新验证，必要时改为测量实际表头。

拖拽侧也修改了 DOM 假设：

```ts
// 源码节选
const rowRect = (event.target as HTMLElement)
  .closest('[data-row-key]')
  ?.getBoundingClientRect()
```

通过行标识定位，能够减少对具体 `tr` 标签结构的依赖。滚动容器查询则同时覆盖普通表体与虚拟 holder，使边缘拖拽滚动作用到正确容器。

不过，`.ant-table-tbody-virtual-holder` 等选择器仍与组件库 DOM 结构耦合。升级组件库时，除了“列表能显示”，还要复测拖拽定位、边缘自动滚动和折叠树节点后的目标行。

图片加载导致的可变行高、超长列表和单元格嵌套表格，也应加入样本。它们会影响虚拟列表对高度的测量与滚动稳定性，无法靠一次静态截图验收。

## 7. 加载状态正确，不代表返回结果一定最新

需求表通过计数器记录进行中的数据请求：

```text
请求开始：pending += 1
请求结束：pending -= 1
loading = pending > 0
```

它解决了一种真实的反馈错误：A、B 两个请求重叠，A 先结束时不能立刻把 loading 关掉，因为 B 还在进行。

但这套计数器没有表达响应顺序：

```text
旧请求 A 开始
新请求 B 开始
B 返回
A 随后返回
pending 最终为 0，但 A 的数据仍可能比 B 旧
```

当前请求函数包含 `setListData` 等副作用。即使外层请求库对自己的结果做了保护，也需要单独检查函数内部更新是否被正确限制，不能仅凭引入了请求库就推断所有状态都不会被旧响应覆盖。

对于筛选、工程或版本切换频繁的场景，可考虑请求代数与上下文标识：只有仍属于当前上下文的结果，才能更新列表、展开行和选中状态。这是需要继续验证的设计方向，本文不将其描述为这次计数器已经提供的能力。

相关竞态可参考[请求合并与刷新边界](/notes/atom-request-coalescing/)。

## 8. 这次验证证明了什么

我从固定提交提取了清洗函数与模块缓存，在 Chromium 中运行，使用锁文件对应的 DOMPurify `3.4.12`。保留原清洗与缓存逻辑，只移除模块导入、类型以及 React 展示层，再附加测试读取入口。

**12 项定向检查通过**，覆盖：

- 脚本、事件属性与活动链接被移除。
- 允许的 Quill 类与颜色保留，布局和图片 CSS 被剔除。
- SVG data 图片拒绝，历史反斜杠地址规范化。
- 命中不重复计数，命中后刷新最近使用顺序。
- 条目数与累计字符预算受限，超大结果不进入缓存。

这些是有限样本的行为检查，不构成完整安全审计；也没有执行整张需求表的拖拽、虚拟行高或性能基准。

如果进入性能验收，我会固定数据集、列配置、设备和浏览器版本，分别观察：

| 操作 | 需要记录的指标或现象 |
| --- | --- |
| 首次打开 | 请求、数据处理与首次可读之间各阶段耗时 |
| 连续滚动 | 长任务、帧耗时、空白与跳动 |
| 来回滚动同一区间 | 清洗调用次数、缓存命中与内存趋势 |
| 编辑后返回列表 | 新内容是否立即可见、旧缓存是否误用 |
| 拖拽靠近边缘 | 滚动容器与目标行是否正确 |
| 快速切换筛选范围 | loading 与最终内容是否分别正确 |

技术负责人对性能工作的贡献，应当体现在这样的拆分里：减少挂载数量、压低单格工作量、限制缓存生命周期、保证交互状态，各自有明确的验证方法。只有把成本和行为一起说清楚，团队才知道下一轮优化应该改哪里。
