建模助手执行到一半，用户切换了页面；删除操作等待确认，服务进程发生重启；模型已经改了数据，但连接中断，浏览器只收到半段文字。

这些情况会迫使我们回答一个问题：**这项任务究竟由谁持有状态，谁有资格继续执行？**

如果答案只是“聊天记录里应该能看出来”，助手就很难成为可靠的工程工具。文字可以描述计划，却不能替代事务回执、待确认命令和执行租约。

SE-MBSE 最近这轮内置助手实现，使用 AgentScope Harness 组织模型推理与工具调用，由业务宿主控制身份、工作区、执行和恢复。本文基于 `feature/v2.5.0/normal` 的 `4918e0d27813a06f7496bd387758e7f3d474ed20`，讨论的是 `components/aiAssistant` 新入口及其后端，不是早期独立演示面板。

## 1. 让框架负责推理，让宿主负责业务事实

当前 MCP 模块引入 `agentscope-harness:2.0.4`。但宿主没有把所有能力默认交给框架。

`AgentScopeRuntime` 配置模型、工具、状态存储和文件系统，替换部分默认中间件，并关闭 Shell、Web、动态子代理等不属于当前建模任务边界的默认入口。业务工具通过 `AiAssistantToolBridge` 复用现有 MCP 执行器。

职责大致如下：

| 层次 | 主要职责 | 关键事实来源 |
| --- | --- | --- |
| 前端助手 | 展示文字、工具结果、问题、确认和任务进度 | 服务端事件与历史 |
| `AiAssistantService` | 会话、权限、工作区、人工交互、执行控制 | 持久化运行状态与工具回执 |
| `AgentScopeRuntime` | 推理循环、工具适配、上下文和子任务 | 模型输出、框架状态 |
| `AiAssistantToolBridge` | 可信参数绑定、工具目录裁剪 | 已认证身份与会话工作区 |
| MCP 项目工具 | 正式建模行为、事务与操作记录 | 真实模型和提交结果 |

最重要的一点是：模型提出调用，宿主决定这次调用能以什么身份、在哪个工作区、带着哪种确认状态执行。框架自身的执行状态不能替代业务提交状态。

## 2. 一次对话首先绑定工作区，再进入推理

`AiAssistantService.chat()` 开始时先检查助手权限，解析工作区，读取并校验用户选择的模型连接，再创建或恢复会话。

已有会话需要核对用户与工作区归属。运行中、待回答、待确认、历史保存异常等状态，也会影响能否接收下一条消息。

这意味着 `conversationId` 不只是聊天框的列表键。它关联着：

- 已使用的请求标识；
- 当前模型连接描述；
- 待确认命令或待回答问题；
- 尚未查清的写入；
- 框架运行状态与可见历史；
- 执行租约和存储版本。

只读模式也不只由用户开关决定。已发布工作区、用户指定只读，以及尚有未核实写入的会话，都会使本次执行进入只读路径。

这一点直接影响恢复：存在未知结果时，助手可以继续查询事实，但不能在原结果尚未查清时继续修改模型。

## 3. 写入前先留下“还有一笔结果未核对”

在 MCP 层，操作记录解决一次命令的提交事实。助手层还需要知道：它是否发起过一笔写入，却没来得及处理回执。

`toolResult()` 的顺序很关键：

```text
确认这是写工具
  → 将 requestId 放入 unresolvedOperations
  → 持久化运行状态
  → 调用 MCP 工具
  → 解析回执
  → 已知结果则清除；未知结果则保留
  → 再持久化
```

如果顺序反过来，先写模型，再登记运行状态，进程可能在两者之间退出。会话恢复后只看见一句未完成的自然语言，却不知道已经发生过写入。

当前实现接受的已知操作状态包括 `SUCCEEDED`、`APPLIED_WITH_WARNINGS`、`FAILED_NO_COMMIT`；部分明确发生在执行前的参数或权限拒绝，也能清除未决记录。无法确认的情况继续保留请求号，拿到操作号后再补充。

查询 `get_model_operation` 得到可确认结果时，宿主会清理对应记录。这条恢复路径依赖实际回执，不靠模型自行声称“刚才应该没成功”。

它仍然不是跨数据库与会话存储的分布式事务，而是用持久化标记缩小遗忘写入的窗口，并让剩余不确定性显式阻断后续写入。

## 4. 人工确认要保存具体命令

助手准备删除一组对象时，不能只保存“用户同意删除”这句话。

因为模型下一轮可能重新生成参数。用户批准的是第一次看到的对象，实际执行的却可能已经变成另一组。

当前流程先通过工具查询删除影响；当返回需要确认或未能明确免除确认时，服务端保存一个待确认对象，其中包含工具调用、已经绑定工作区的参数以及交互信息，再发送 `confirmation` 事件。

用户返回确认标识和是否同意后，服务端重新检查会话与待确认状态，取出**先前保存的参数**，再附加可信的确认标记执行。

```text
模型提出删除
  → 宿主绑定工作区和请求号
  → 查询实际影响
  → 保存具体命令，结束本次流
  → 用户按 confirmationId 作答
  → 宿主恢复已保存命令
  → 重新进入受控执行链
```

确认解决的是授权问题，不代表数据从此被冻结。真正执行时，工具链仍然承担前置条件和当前权限校验。

`ask_user` 采用类似思路：问题对象、调用和运行状态被保存，回答用于恢复原任务。没有回答时，不能把一次 HTTP 结束理解成整项任务完成。

## 5. 历史记录和运行快照解决不同问题

历史记录服务于用户回看；运行快照服务于机器续做。

仅保存“用户说了什么、助手回答了什么”，无法恢复工具调用与结果配对、待回复标识、确认命令、未知写入列表和执行所有权。因此当前实现同时维护可见会话历史与框架原生状态。

运行存储接口要求以版本号做比较更新：只有调用方持有的版本仍是最新版本，才能保存新状态。创建使用初始版本，后续写入递增版本；涉及会话历史的保存还要求与运行状态更新保持原子一致。

这就是 CAS，也可以把它理解为“保存前确认我没有落后于另一位写者”。

### 租约避免两台宿主同时续跑同一会话

运行状态还保存 `leaseOwner` 和 `leaseUntil`。当前执行期间将租约延长到约两分钟后，并用约十五秒的心跳刷新运行状态。开始执行前取得会话租约，恢复时检查是否仍由另一个实例持有。

这处理的是同一个会话被重复接管的问题。它不等于对所有工程写入提供了分布式互斥，也不能代替 MCP 写入层自己的幂等和数据一致性规则。

恢复时还有一个务实的限制：如果只有旧版文字历史，缺少可用的原生运行状态，系统会把文字作为上下文恢复，而不是把历史工具调用重新执行一遍。

历史中的“执行过”必须被当成已发生事件，不能被误读成待执行计划。

## 6. 并行分析和并行改模型要分开

子任务适合做需求整理、模型审查，或者独立范围的建模分析。当前实现使用自定义委派逻辑管理子任务，限制它们不能取得当前模式以外的 MCP 工具。

这里也有一个需要如实描述的细节：需求分析、模型审查角色在未显式指定工具时默认使用只读工具；角色名称本身并不能代替所有权限限制。最终仍要看传入的工具子集和宿主执行检查。

在真正调用业务工具的回调处，`AiAssistantService` 使用同一轮运行的 `toolMonitor` 协调主代理与子代理调用。获得锁之后，还会再次检查子任务是否已经取消，避免任务在等待期间停止，却仍然继续执行。

由此形成的取舍是：

> 允许任务分析并发推进，同时收拢同一轮运行中的实际建模工具调用。

这样做会牺牲部分工具吞吐量，但建模变更往往共享工作区、引用和未决回执。减少并发交错，能让每次调用观察到更清楚的前置状态，也让失败后的核对更容易。

如果以后要提高写入并行度，首先需要证明目标依赖互不冲突，而不是简单打开框架的并行工具开关。

## 7. 长任务需要整理上下文，但不能丢掉操作事实

长时间建模会产生大量查询结果和元素标识。如果全部留在模型上下文里，成本与上下文窗口都会成为限制。

直接截掉历史又有风险：模型可能忘记某个创建已经提交，或忘记某次结果仍是未知，从而重复执行。

`AiAssistantContext` 因此采用“先归档，再摘要”的顺序：

1. 找到可以整理的历史前缀，保留最近消息以及工具调用与结果的边界；
2. 将完整前缀保存为可读取的 JSONL 记录；
3. 生成包含目标、关键 ID、提交状态、待办和阻塞原因的工作摘要；
4. 只有摘要确实缩小了上下文，才替换旧前缀。

归档失败就保留原始上下文；摘要请求失败交给宿主处理，不用一个占位摘要假装压缩成功。摘要过长时，先保存完整摘要，再把有限节选和文件路径留在工作上下文中。

工具结果的处理也有区别：较长的只读结果可以归档后按需检索；写工具回执被排除在那条通用结果驱逐路径之外。因为回执中保存的不是普通参考资料，而是决定能否继续操作的证据。

这条设计并不能保证模型永不遗忘。它提供的是可追溯来源，以及比“截断最老消息”更明确的失败边界。

## 8. 用进展判断约束循环，而不只数轮次

当前运行配置把推理轮次上限设得很高，正常长任务不靠一个很小的固定轮数截断。这也意味着必须处理另一种情况：模型反复查询同一批候选，或给同一个失败操作换一个请求号继续尝试。

`AiAssistantProgress` 根据真实调用参数和回执计算稳定签名，忽略 `requestId`、`readToken`、`traceId` 等易变字段。

第一次发现新完成的一组调用没有带来新结果，会提示改变路径；再次重复且没有进展，会在下一轮推理中移除工具列表，让模型解释已完成项、未完成项和阻塞原因。

成功写入可能改变之前的失败条件，因此会清理相关观察状态。等待子任务也不被简单当成重复调用。

这比“最多调用十次工具”更贴近业务，但仍是启发式控制。模型不断生成不同却无用的查询，可能逃过重复检测。并发限制、取消机制、模型请求超时和运行观测仍然必要，不能只靠这个中间件控制成本。

## 9. SSE 的网络结束与业务结束不能混为一谈

前端通过 `fetch` 发起 POST，再读取 SSE 数据流。`readAssistantEvents` 需要跨网络块拼接帧，正确处理中文 UTF-8 多字节、CRLF 和心跳。

真正影响用户体验的，是终态定义：

| 事件 | 当前请求是否结束 | 整项任务的含义 |
| --- | --- | --- |
| `complete` | 是 | 本轮执行结束，结合工具回执判断结果 |
| `error` | 是 | 本轮异常，可能已有提交 |
| `confirmation` | 是 | 等待用户确认，尚未完成 |
| `question` | 是 | 等待用户回答，尚未完成 |

收到这些事件后，解析器立即结束本次读取，不等待代理或服务器关闭 HTTP 连接，也不再消费后续帧。

反过来，读到了 EOF 却没有业务终态，就报“执行结果待核对”。网络断开不能证明操作回滚。

前端刷新逻辑也体现了同一原则：任何终态只要携带 `changed`，都可能需要刷新模型树与视图，包括报错和等待交互。因为任务可能先成功创建了元素，随后才在下一步停下来。

用户点击停止时，系统取消继续执行；已经提交的操作仍以真实模型为准。把“停止生成”和“撤销建模”放在同一个按钮含义里，会给用户错误承诺。

## 10. 这次文章做了哪些实际验证

我从固定提交提取了原始 `stream.ts` 和 `context.ts`，只擦除 TypeScript 类型后在 Node 中运行，没有重写一份理想化解析器来证明自己。

配套实验验证了：

- 中文事件按每个字节切块后仍能正确还原；
- CRLF 和心跳不会打乱事件顺序；
- 四种业务终态都能在连接仍开放时结束；
- 终态之后的帧不再进入界面；
- 没有终态的 EOF 会报错；
- 等待网络期间可以取消；
- 非 SSE 响应和损坏 JSON 不会变成聊天正文；
- 选中元素 ID 保持字符串精度并过滤无效值。

同一套实验还直接编译了 Java 回执类，验证其错误分类和恢复字段。一共 12 项外层检查通过；这不是对模型服务、数据库、代理网络和多实例接管的端到端验证。

## 11. 架构上真正需要坚持的边界

这轮实现的价值，在于让任务状态从自然语言里走出来，成为平台可以检查、保存和恢复的对象。

模型负责理解目标和提出步骤；宿主负责工作区、工具权限、交互和执行所有权；领域工具负责实际修改与提交证据；前端负责准确表达当前状态。

后续演进仍应围绕几个具体问题验证：租约接管与网络抖动的时序、长任务持续生成新调用的成本、上下文摘要能否保留关键约束，以及跨实例写入协调。它们都不能通过一句“支持 Agent”自动得到保证。

对我来说，成熟的建模助手最重要的能力，是在任务顺利时持续推进，在结果不确定时停在正确的位置，并把足够的事实留给下一次决策。

## 源码线索

后端主要位于 `server/mbse-platform-mcp/src/main/java/com/shareetech/mbse/platform/mcp/assistant/`：

- `AiAssistantService.java`：会话、确认、未决写入、租约和流事件。
- `AgentScopeRuntime.java`：框架配置、工具适配与子任务运行。
- `AiAssistantContext.java`：完整归档与上下文摘要。
- `AiAssistantProgress.java`：重复结果与无进展判断。
- `AiAssistantDelegation.java`：子任务和工具范围。

前端位于 `client/src/appModeling/components/aiAssistant/`，重点是 `api.ts`、`stream.ts`、`context.ts` 和 `aiAssistant.tsx`。
