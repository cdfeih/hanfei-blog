协同编辑中的“在线用户”看似只是一个头像列表，背后却同时关联连接、工程、文档、撤销记录和仿真资源。关闭一个标签页，如果只删除一个 WebSocket 对象，相关状态可能仍然留在系统里。

SE-MBSE 的 `CollaborativeSessionManager` 把这些关系放到明确的会话管理边界中。阅读它时，需要先区分用户与连接。

## 一个用户可以拥有多个会话

用户可能同时打开两个标签页，甚至在同一工程里查看不同文档。此时一条连接关闭，不等于这个用户已经离开工程。

当前代码在准备发布工程用户离线事件前，会检查该工程中是否仍存在属于这个用户的打开会话。只有没有其他活跃连接，才继续发出用户离线事件。

这个判断避免把传输层事件直接等同于业务事件：

```text
连接关闭
  → 从连接所属集合移除
  → 查找同一用户在该工程的其他活跃连接
      → 仍有连接：用户仍在线
      → 没有连接：发布工程用户离线事件
```

“会话离开”“用户离线”“工程无人使用”是三个不同结果，后续处理也应该据此选择。

## 清理是一张资源关系表

当前管理器维护工程会话集合和文档会话集合。明确断开时，会移除相关会话、清理空集合，并处理冲突状态、会话撤销重做栈、离开通知和仿真资源事件，最后清除当前线程里的相关上下文。

可以把清理对象按生命周期分类：

| 资源 | 归属 |
| --- | --- |
| 连接和会话属性 | 单次会话 |
| 会话的撤销重做记录 | 单次会话的编辑过程 |
| 文档在线成员 | 文档与会话的关系 |
| 工程在线状态 | 工程与用户的关系 |
| 线程上下文 | 当前执行过程 |

这张表能帮助发现遗漏：如果新增一种协同能力，却没有说明状态由谁清理，它通常会在异常断开路径上暴露问题。

## 事件清理之外，还有定期兜底

当前实现已经配置了定期清理：启动后等待一段时间，再周期性清除关闭的会话及空集合，工程集合被清空时还会处理相关画布冲突状态。Bean 销毁时关闭清理线程池。

因此，不能继续沿用旧说明，把这个类写成“还没有定期资源清理”。

同时，定期清理与明确断开时的清理动作并不完全相同。当前定期流程主要针对集合及相关画布状态；是否补足了所有离线业务事件，需要逐项比较，而不是假定一个定时器就能覆盖全部异常退出。

## 并发容器不等于整个过程原子化

顶层使用 ConcurrentHashMap，解决的是容器操作的一部分线程安全问题。但“检查集合为空，然后移除集合，再释放其他资源”是多个动作组合。

如果检查与移除之间有新连接加入，处理是否仍然正确，需要结合基类的集合操作与并发控制一起验证。仅凭容器名字，不能得出“清理流程没有竞争”的结论。

更可靠的验证方式，是让加入和离开同时发生，观察新会话是否被误删，以及重复清理是否造成额外离线通知。

## 测试应该从用户行为出发

我会优先检查这几条路径：同一用户打开两个标签页，关闭一个；关闭最后一个；切换文档但不离开工程；连接已经关闭却没有及时移除；清理过程中又加入新会话。

每条路径都需要观察资源结果，而不只观察连接数量：在线头像是否正确，撤销栈是否归属正确，文档成员是否清除，线程上下文是否残留。

协同系统的稳定性，常常取决于离开路径是否与进入路径一样完整。把每项资源的拥有者和释放条件写出来，清理逻辑才容易被维护。
