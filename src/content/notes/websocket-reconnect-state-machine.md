建模平台中的长连接常常同时承担系统通知与请求响应。连接断开后，用户关心的是“还能不能继续操作”，而客户端代码可能只关心“过几秒再试一次”。

SE-MBSE 的系统消息连接管理类提供了一个适合分析的切口：初始化、连接成功通知、发送前等待、手动关闭和退避重连，都集中在一个对象中。

## 一个连接对象，有几种不同状态

当前 `init` 会先检查实例是否存在，避免重复创建；连接成功后设置 `connected` 并发出通知。发送前的 `beforeSend` 则检查连接状态，没有连接时等待成功事件。

这里至少存在三种不同事实：

| 判断 | 真正表达的含义 |
| --- | --- |
| 实例存在 | 管理对象已经创建 |
| connected 为 true | 最近一次回调认为连接可用 |
| 某次请求成功 | 业务响应已经返回 |

把它们视为同一件事，会让状态转换出现缝隙。例如，连接关闭后实例依然存在，并不表示重新调用初始化就会创建新连接。

## 退避参数只是策略的一部分

当前类配置了重试次数上限、最小和最大等待时间，并在重试时增加次数、延长等待。它表达了避免持续高频重试的意图。

但重连回调最终仍调用 `init`，而 `init` 又有“实例存在直接返回”的判断。在这一层代码中，看不到重建前清空实例的动作。因此，不能仅凭 `attemptReconnect` 的存在就宣称自动恢复已经完整生效；还需要检查底层 Websocket 封装是否接管重连。

同样，成功后重置次数，并不自动证明所有定时器、旧监听器和等待中的请求都已经清理。

## 发送前等待需要有终点

`beforeSend` 的思路很自然：未连上时先等。但如果没有 token、连接一直失败，或者成功事件被错过，等待者如何结束？

一个可复用的连接层应明确以下结果：连接成功、连接失败、等待超时、调用方取消。否则界面中的 loading 可能被一个永不结束的 Promise 固定住。

建议的状态示意如下：

```text
idle → connecting → open
          ↓          ↓
        failed ← disconnected
          ↓
       retry-wait → connecting

任意活动状态 → 手动关闭 → closed
```

这是建议的设计表达，不是对现有类所有状态的逐字描述。它的作用是帮助团队逐条检查：谁创建连接，谁释放旧实例，谁能结束等待。

## 手动关闭与意外断开要分开

退出登录、切换账户或主动离开应用时，不应继续重连旧身份。当前类已有 `isManualClose` 标记，这是必要区分。

审查时还要看设置标记、关闭连接和清理定时器的顺序，以及晚到的回调是否可能重新激活连接。更稳妥的实现可以用连接代次识别旧回调，让旧连接的成功事件不能覆盖新连接的状态。

## 传输恢复之后，还要恢复业务

连接重新打开，只说明通信通道可用。断线期间漏掉的通知是否补拉、未完成的请求是否重试、许可或订阅是否重建，都需要各自的业务策略。

尤其不能无条件重发所有写操作。请求可能已经在服务端完成，只是响应没有送到客户端。重试需要结合操作标识和服务端幂等语义。

验证时可以人为断网，再检查等待请求是否结束、重复重连是否只产生一个连接、主动关闭后是否停止重试，以及业务状态是否重新同步。相比只看控制台打印“连接成功”，这些现象更接近用户真正需要的恢复能力。

## 实现线索

对应系统消息 `wsStore` 的 `init`、`beforeSend`、`close` 和 `attemptReconnect`。本文分析上层生命周期，没有将未核实的底层重连行为写成已知事实。
