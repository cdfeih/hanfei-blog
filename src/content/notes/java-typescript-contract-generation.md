前后端一起迭代时，DTO 改动、枚举新增和接口路径调整经常需要重复同步。手工维护两份类型定义，很容易让差异直到联调时才暴露。

SE-MBSE 用脚本扫描 Java 类型、枚举和 Controller，生成前端模型与接口文件。它还组织了 WebSocket 策略扫描及 schema 生成任务。这个方向能减少机械工作，但生成文件数量并不能直接说明契约已经准确。

## 先把输出分成不同责任

当前脚本的任务序列包括清理生成目录、扫描源码、处理常量和枚举、生成类型、生成 API，以及其他辅助产物。

这些产物承担不同作用：TypeScript 接口约束编译期使用，API 包装减少调用样板，枚举选项帮助界面展示，schema 则需要进一步确认是否在运行时真正接入校验。

生成了 schema 文件，不等于所有请求和响应都已经验证。必须继续检查消费方有没有调用，以及失败时怎样反馈。

## Long 映射为 string，是通信契约

当前类型映射把 Java 的 `Long` 和 `long` 转成 TypeScript `string`。它针对的是 JavaScript Number 的安全整数范围：可精确表示的整数上限为 `2^53 - 1`，并不能覆盖所有长整型标识。[Number.MAX_SAFE_INTEGER 说明](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/MAX_SAFE_INTEGER)

可以用一个独立示意表达前端的意图：

```ts
interface ElementSummary {
  id: string;      // 标识只用于关联，不参与算术
  name: string;
  revision: number;
}
```

关键是后端实际 JSON 也必须按字符串发送该标识。只把前端类型写成 string，无法恢复解析前已经丢失的精度。

相同的审查还应覆盖高精度小数。当前映射里 BigDecimal 对应 number，这不代表所有需要精确十进制语义的场景都能无损表达；应按具体字段的业务含义制定策略。

## 必填、非空与默认值不是同义词

当前脚本会根据若干校验注解判断必填，也将 `@Size` 中大于零的 min 纳入判断。

这是值得仔细审查的语义映射。字段有长度约束，未必就等同于网络请求里绝不允许缺失；后端校验组、默认值和序列化策略，也可能改变字段的实际使用方式。

因此生成器应分别考虑：字段是否存在、是否允许 null、值满足什么约束。简单地把所有约束都压成一个 TypeScript 问号，很难完整表达接口契约。

## 扫描能力需要样例约束

脚本中可以看到 Controller 映射识别、内部类与 record 处理，以及泛型解析等逻辑。这些都是项目演进后会遇到的真实语法形态。

随着输入语法越来越丰富，仅凭文本正则很容易遗漏注解排列、多行声明或复杂泛型。即使某些后续任务已经采用 AST，也仍需确认各阶段支持的语法范围，不能把整个工具笼统称为完整 Java 编译器。

最有价值的回归材料是一组小型后端样例及预期输出，覆盖：长整型 ID、可空字段、嵌套列表、泛型包装、内部 record、枚举和多种路由注解。

## 不要直接用生成结果证明自己正确

建议先生成到临时目录，再与预期快照比较；随后检查前端类型能否编译，并用独立 JSON 样例验证运行时含义。生成脚本已经支持指定输出目录，这为隔离验证提供了便利。

执行前还应知道工具会清理哪些生成目录。代码生成不能顺便覆盖人工维护的文件；生成区与手写扩展区需要明确分开。

团队协作上，可以把“后端契约变更 → 生成 → 审查差异 → 编译与样例验证”放进一个可重复流程。代码评审关注字段语义和兼容性，而不是逐行检查机械格式。

自动化真正减少的是重复同步的成本。契约的含义仍需要人定义，再由样例和检查长期守住。
