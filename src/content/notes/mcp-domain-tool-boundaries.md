一个模型能够调用 `create`，离它能够正确建模还有多远？

拿活动图上的一个判断分支来说。用户要求“当温度超过阈值时进入保护流程”，助手画出两条线，再给其中一条标上条件文字。看起来任务已经完成，但模型里可能根本没有可解析的守卫表达式。后续做语义校验、代码生成或重新打开图形时，问题才出现。

这是我在整理 SE-MBSE 最近这轮 MCP 实现时最关注的一条边界：**工具必须表达系统真正支持的建模行为，并返回能够验证这种行为的证据。**

本文基于 `feature/v2.5.0/normal` 的 `4918e0d27813a06f7496bd387758e7f3d474ed20`，记录截至 2026 年 10 月 20 日的实现。文中的简化代码用于解释执行顺序；具体标识和业务例子均为示意。

## 1. 先分清协议层解决了什么

MCP 为工具发现和调用提供了统一接口：客户端取得工具列表、理解输入 Schema，再发起工具调用。工具自身失败可以通过结果中的 `isError` 表达，与协议层请求错误区分开来。这是协议提供的协作基础。[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

但协议并不替建模平台决定以下问题：

- 调用者能否修改这个工程、分支和版本？
- 一个关系到底改变语义模型，还是只改变图上的呈现？
- 方法返回之后，数据有没有提交，派生事件有没有结束？
- 结果过长时，哪些字段绝不能丢？

SE-MBSE 的实现因此分成了三段：协议接入、统一工具执行、正式领域能力。下面画的是职责关系，省略了异常分支。

[![外部 MCP 和内置助手在统一执行器汇合，再进入项目工具和正式业务服务](/images/articles/mcp-execution-boundaries.svg)](/images/articles/mcp-execution-boundaries.svg)

手机阅读可点击图片查看大图。

外部客户端经过 HTTP 身份认证；内置助手经过服务端可信桥。两条入口最终进入同一个 `McpToolExecutor`，项目工具再调用已有业务服务。

这避免了一个长期成本很高的分叉：编辑器维护一套建模规则，AI 接口再维护一套。后一套开始时通常很简单，后来却不得不追上版本隔离、数据锁、语义引用、派生事件和图形刷新等全部规则。

## 2. 工具注册是一份显式契约

`McpConfiguration` 收集显式声明的 `McpTool<?>`，校验工具名称与重复注册，生成输入 Schema，再把回调绑定到统一执行器。

工具实现承担自己的权限判断和业务执行，基础执行器处理共同约束。这样新增工具不会顺手绕开参数校验、身份恢复或输出限制。

这里还有一个容易忽略的实现细节：注册和调用需要保留 Spring 代理。如果为了取得“真实类”而绕过代理对象，就可能绕开方法级权限或事务拦截。工具能被发现，不代表它应该脱离原来的调用机制。

当前接入选择了无状态、同步的服务端配置，并关闭部分自动扫描和转换入口。这是本项目为了控制工具暴露范围作出的部署选择，不是 MCP 对所有服务器的统一要求。

## 3. Schema 首先要保护数据精度

建模平台大量使用 Java `Long` 标识，浏览器和模型接口却经常把 JSON 数字交给 JavaScript `Number`。

例如：

```js
String(Number('9223372036854775807'))
// '9223372036854776000'
```

如果调用链先把标识当数字读入，再转回字符串，精度早已丢失。服务端收到的仍然可能是合法整数，但已经不是用户选中的那个元素。

所以本实现把跨边界业务 ID 表达为字符串。`McpToolSchemas` 递归检查生成的 Schema，发现 `integer/int64` 就拒绝这类工具契约。前端的 `getAssistantSelectedIds` 同样保留字符串，并在送给助手前处理收藏前缀、去重、过滤虚拟导航节点以及超出有符号 Long 上限的值。

这不是单靠提示词能够解决的问题。提示词可以告诉模型“请传字符串”，Schema 和反序列化层则要确保传错时确实失败。

`McpToolExecutor` 的映射器还关闭了几类常见宽松转换：

| 输入问题 | 如果宽松接受 | 当前边界的意义 |
| --- | --- | --- |
| 用小数填整数 | 可能悄悄截断 | 让模型明确修正参数 |
| 用字符串填布尔值或整数 | 混淆字段类型 | 保持 Schema 与执行行为一致 |
| 多传未知字段 | 拼错字段被静默忽略 | 及时暴露模型误解 |
| 用数字选择枚举 | 依赖内部排列顺序 | 要求表达稳定的枚举语义 |
| 把业务 ID 传成数字 | 可能已发生精度损失 | 提供字符串修正方向 |

严格校验也会增加首次调用失败的概率。这里的取舍是：接受可纠正、无副作用的参数失败，避免一次“看似成功”的错误写入。错误信息因此也必须可操作，例如指出字段路径、合法枚举和恢复方向，同时避免回显不必要的输入或内部异常。

## 4. 身份不能跟着模型参数走

外部 MCP 请求先由 `McpAuthenticationFilter` 认证个人凭证。它限制 Authorization 头的形式，检查 Origin 策略，按实际读取字节数限制请求体，再把认证得到的凭证标识放进服务端请求上下文。

这个标识属于可信传输信息，不来自模型可填写的工具参数或客户端 `_meta`。

工具执行时还要再次验证凭证。原因很具体：HTTP 认证通过与真正执行之间存在时间差，凭证可能被撤销，权限也可能发生变化。一次入口认证不能成为后续调用永不过期的通行证。

随后执行器组合检查凭证范围、当前用户权限，以及工具对目标数据的授权。权限范围和业务权限是相交关系：凭证允许某类工具，不代表用户就有权修改任何工程。

### 为什么上下文恢复值得单独设计

正式业务代码依赖的上下文不只有用户 ID，还包括安全上下文、令牌、版本和密级等信息。

`McpContext` 进入作用域时保存原上下文，清理残留，再安装当前身份；退出时清理本次上下文，并恢复先前状态。这里“恢复”比简单 `remove()` 更重要，因为调用可能嵌套在已有业务作用域中。

可以把它理解成一个必须成对执行的资源操作：

```java
// 执行结构示意，省略具体类型和异常转换
previous = captureContexts();
try {
    clearContexts();
    installCurrentIdentity();
    authorizeAndExecute();
} finally {
    clearContexts();
    restoreContexts(previous);
}
```

否则，同一线程复用、嵌套调用或异常返回都可能把上一次的版本信息带到下一次操作里。这种问题很难从工具返回的文本里发现。

## 5. 工具语义要和编辑器的正式能力对齐

活动图的分支条件提供了一个很好的检验场景。

在当前实现中，真实条件应通过 `set_model_expression` 写入，并通过 `get_model_expression` 读取验证。决定节点的名称、线条的显示名称、以及关系上的表达式，承担不同职责。

因此，“条件已经添加”至少需要回答三件事：

1. **目标是谁**：表达式挂在正确的语义元素上了吗？
2. **内容是什么**：系统能解析这份表达式，得到预期结构吗？
3. **如何显示**：对应呈现对象是否存在，显示设置是否正确？

把图形画出来，只证明了其中一部分。

类似的边界也出现在属性类型和单位设置里。`set_model_attribute_declaration` 复用正式属性能力，处理类型与单位引用，而不是让模型任意写一个字符串到“类型名称”字段。

标准库中的类型、单位还可能通过 URI 或限定名引用，并不一定都有当前工程数据库中的元素 ID。如果工具强制所有引用都先转换为本地元素 ID，它就把存储假设错误地提升成了领域约束。

这也是为什么“提供一个通用字段更新工具”看似省事，实际上经常把最难的工作推给模型：模型必须猜哪些字段组合才能形成合法语义，而平台原来就有规则，却没有通过工具契约表达出来。

### 能力查询也必须来自运行时

不同图种、目标类型和配置下，可执行的自动化操作并不相同。当前的 `get_model_automation_options` 从实际运行配置返回候选、可执行性和原因，而不是让模型一直依据提示词里的静态菜单尝试。

这里值得保留一条原则：**静态说明负责教模型如何思考，运行时查询负责告诉模型此刻能做什么。**

否则平台配置更新之后，提示词很容易继续宣传已经不可用的操作。

## 6. 内置助手为什么还需要一层可信桥

内置助手和服务端处于同一进程，没有必要为了复用工具再向自己发 HTTP 请求。但直接调用业务方法，又会丢失 MCP 执行器已经建立的边界。

`AiAssistantToolBridge` 采用进程内适配：

- 复用当前已注册、可用的工具目录；
- 对工具参数执行严格 JSON 解析；
- 拒绝嵌套的身份注入字段；
- 去掉模型提供的工作区和版本，再绑定服务端会话解析出的工作区；
- 写工具的 `requestId` 由宿主绑定；
- `confirmed` 来自宿主保存的审批状态；
- 最后仍交给 `McpToolExecutor` 执行。

这层桥的价值，是把“模型提出的操作建议”转换成“具备可信执行上下文的命令”。模型可以建议修改哪个元素，却不能通过参数把自己升级成另一个用户，或者伪造一次已确认的删除。

批量工具也复用同一套绑定逻辑。子命令的请求标识根据父请求和下标确定，工作区与确认状态继续由宿主控制，避免批次内部出现第二套信任规则。

## 7. 输出契约和输入契约一样重要

查询结果可以很长，写入回执却不能因为响应长度限制而失去恢复入口。

执行器按 UTF-8 字节限制输出。普通结果过长，可以明确返回超限；对于实现了 `McpOperationReceipt` 的结果，则优先压缩成保留操作标识、状态和后续查询入口的回执。

这背后的区别是：查询失败通常还能重新查询；写入之后丢掉 `operationId`，调用方可能无法判断应该等待、查询还是重试。

因此，工具接口设计不能只列输入字段。还要提前定义“成功证明”“已提交但有警告”“无法确认结果”分别如何表达。下一篇会沿着这条线继续拆解。

## 8. 这次实现让我重新理解了工具数量

工具多，不等于系统更懂建模。一个工具是否值得暴露，我更愿意看四件事：

1. 它是否对应真实、稳定的业务动作；
2. 它是否复用了正式权限和领域规则；
3. 调用失败时，模型能否修正或停止；
4. 调用成功时，用户能否验证实际改变。

当前实现仍有明确边界，例如复杂复制和通用撤销不能因为接入了 MCP 就自然获得。工具层应该如实表达这些缺口。

MCP 接入的工程价值，最终体现在模型是否能沿着平台已有的正确路径完成工作，而不只是让一次 `tools/call` 返回 200。
