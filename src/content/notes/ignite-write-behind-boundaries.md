建模操作执行成功后，后续任务立刻从数据库读取，是否一定能看到这次修改？回答这个问题，需要先确认“成功”发生在哪一层。

SE-MBSE 的数据缓存同时设置了 `writeThrough=true` 和 `writeBehindEnabled=true`。前者连接外部存储写入通道，后者让外部存储更新经过写后缓冲。因此，缓存操作完成与外部数据库完成不是同一个时刻。这也符合 [Ignite 外部存储文档](https://ignite.apache.org/docs/ignite2/latest/persistence/external-storage) 对 write-behind 的说明。

这篇文章检查的重点，是项目如何使用这条通道，以及分支装载和清理有什么前提。

## 从配置走到实际 JDBC Store

`IgniteCacheManager` 创建业务缓存时配置事务模式，并设置写后批量大小、刷新阈值和刷新周期，外部存储由 `JdbcEntityStoreFactory` 创建。

```text
业务变更
  → Ignite 缓存事务
  → 缓存提交，对缓存读取者可见
  → 写后缓冲
  → JdbcEntityStore / AbstractJdbcStore
  → JDBC 写入外部数据库
```

配置中的周期不能直接解释为“数据库最多延迟这么久”。批次执行时间、数据库可用性、积压和失败重试都影响最终延迟。只测接口耗时，会漏掉后半段。

因此需要分别回答：

| 完成点 | 已得到的保证 | 仍需另行确认 |
| --- | --- | --- |
| 缓存事务提交 | 此次缓存事务已结束 | 外部数据库是否完成 |
| 某次 JDBC 批次执行完成 | 该批次执行路径返回 | 目标业务操作是否全部包含其中 |
| 分支可装载标记存在 | 装载流程曾走到标记步骤 | 后续写后数据是否全部持久化 |
| 缓冲大小瞬时为零 | 该观测时刻没有被计入的缓冲项 | 特定版本的持久化屏障是否成立 |

最后一行尤其不能代替按操作或按版本确认的完成协议。

## 分支第一次装载为什么需要锁

`loadCacheIfAbsentByBranch` 不只是执行一条查询。它需要把一个分支涉及的多个表装入缓存，并协调“这个分支是否已经可用”的标记。

源码中的关键次序是：

1. 如果当前存在 Ignite 事务，先挂起，最后在 `finally` 恢复。代码说明这里需要避开分支活动缓存与模型缓存的配置差异。
2. 更新分支活动记录，检查装载标记和分支锁状态。
3. 需要装载时取得分支锁，再次检查标记。
4. 对带分支字段的数据表按 `branch_id` 查询，调用缓存的 `loadCache`。
5. 所有表加载结束后，才添加分支已装载标记。

第二次检查避免两个并发请求排队后各装一次。把标记放在末尾，则避免“第一张表刚装好，另一个请求就把整个分支视为可用”。

但这个设计没有凭空获得跨表数据库快照。如果装载过程读取多张表，而外部数据库同时变化，是否一致仍取决于读事务和数据来源约束。源码中的分支锁也不能自动约束绕过该锁的外部写入。

## 部分失败留下什么

构造一个推演场景：分支有 A、B、C 三张表，A 和 B 装载成功，C 查询失败。

此时已装载标记尚未写入，后续请求有机会重新走装载流程；A、B 已经进入缓存的内容却不等于自动回滚。检查异常路径时，应该区分：

```text
“没有 ready 标记”
≠
“缓存中没有这个分支的数据”
```

合理的验证应在第二张或第三张表处注入失败，随后重新进入该分支，检查重试后的记录集合，而不能只断言标记不存在。本文未连接数据库做故障注入，这里给出的是由装载顺序导出的验证场景。

## 清理分支时，不要猜测 delete 的含义

`clearCacheByBranch` 在锁外、锁内检查分支装载状态和活动信息，随后通过缓存 SQL 删除该分支的数据。代码中还留有确认同步完成的 TODO。

看到 SQL DELETE 很容易进一步猜测：“缓存删除会通过 Store 删除数据库，所以清理可能删库。”但继续读实际 `JdbcEntityStore` 会发现：

```java
@Override
public void delete(Object o) throws CacheWriterException {
}

@Override
public void deleteAll(Collection<?> collection) throws CacheWriterException {
}
```

这两个方法当前没有外部删除实现。`loadAll` 也直接返回空 Map；批量分支装载另走显式 `loadCache` 路径。因此不能把通用 CacheStore 的能力说明，直接套成项目此刻的数据库行为。

业务上的版本删除、缓存驻留数据清理、数据库物理删除，是三种需要分别追踪的操作。要判断业务删除如何持久化，应继续查看版本模板对实体字段和版本数据的写入，而不是停在方法名 `delete` 上。

同样，空 delete 也不能证明“清理永远安全”：尚未刷出的写、并发访问和重新装载之间是否有完成屏障，仍需要按实际运行配置验证。

## 用一个队列模型确定要测什么

假设仅作容量推演：每秒进入 800 条待持久化写，数据库稳定处理 600 条，持续 30 秒。忽略同键合并，积压约为：

```text
积压增量 = (800 - 600) × 30 = 6000 条
```

这是构造数据，不是项目压测结果。真实写后实现可能合并同一键的更新，“业务请求数”和“缓冲项数”不能直接相等。

有用的监测至少要能区分入口速度、缓冲积压、重试、数据库批次耗时与业务可接受延迟。仓库有 `CacheStoreMetricsBinder`，列出了缓冲大小和重试等指标，但类上的 `@Component` 被注释了。看到指标代码存在，不代表运行环境已经注册并采集；还需要检查实际 Bean 配置和监控输出。

## 如果后续动作必须读到数据库新值

先确定后续动作能否直接读取同一缓存一致性域。如果必须依赖外部数据库，则需要显式完成条件，例如与业务版本关联的持久化确认，或选用满足要求的同步写入路径。

不能用固定睡眠替代：睡 100 毫秒在空载时可能通过，数据库变慢后就失效。也不能仅凭一次队列长度为零，认定某次操作已经形成可追踪的持久化确认。

我的检查顺序是：先写清“谁读、读哪里、必须包含哪个版本”，再选择等待、重试、失败恢复和清理策略。这样才能判断吞吐量收益是否符合一致性要求。

## 源码定位与验证范围

基线 `67b9805a064b`，核心文件位于 `server/mbse-platform-core/src/main/java/com/shareetech/mbse/platform/core/`：

- `ignite/IgniteCacheManager.java`：缓存配置、分支装载与清理。
- `ignite/sync/JdbcEntityStore.java`：项目实际 Store 覆写。
- `ignite/sync/AbstractJdbcStore.java`：JDBC 写入实现。
- `ignite/metric/CacheStoreMetricsBinder.java`：指标定义和注册状态线索。

本文核对了实现和官方语义，没有运行 Ignite 集群、数据库故障注入或性能测试；没有声称当前代码已经具备持久化完成屏障。
