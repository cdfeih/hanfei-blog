一个数据库迁移脚本能够执行，并不意味着迁移后的数据与原来一致。

对包含元模型配置、JSON、富文本和历史版本的建模平台，这个差别尤其重要：丢掉一个反斜杠，可能让 JSON 变成非法文本；重复执行一段种子更新，可能让用户补充的字段丢失；看到一个同名索引，就跳过创建，也可能留下错误的索引结构。

我在整理 SE-MBSE 的 MySQL 到达梦转换实现时，采用了一条评审主线：**转换工具需要说明它保持了什么语义、依赖哪些前提，以及哪些情况必须交给目标数据库验证。**

下面讨论的是仓库里的受限迁移工具，不是任意 SQL 的通用翻译器。

## 1. 先区分三层正确性

| 层次 | 要回答的问题 | 仅靠什么不够 |
| --- | --- | --- |
| 文本与解析 | 字符串、语句和字段边界是否识别正确 | 全局替换和“文件生成成功” |
| 转换语义 | 转换前后的值、条件与约束是否一致 | 只检查目标 SQL 有没有语法错误 |
| 数据库执行 | 在指定版本、参数、旧数据下，执行和重试结果是否符合预期 | 纯字符串单元测试 |

这三层应当分开验收。否则，“离线测试通过”很容易在交付过程中被转述为“数据库迁移已经验证”。

当前转换器明确假定源文件使用 MySQL 的默认字符串转义口径，目标按 `BACKSLASH_ESCAPE=0` 编码。MySQL 的 `NO_BACKSLASH_ESCAPES` 与 `ANSI_QUOTES` 会改变字符串解释方式，因此 SQL 模式本身也是迁移输入的一部分。[MySQL 字符串字面量文档](https://dev.mysql.com/doc/refman/8.0/en/string-literals.html)

这个前提如果不成立，应调整解析策略或拒绝输入，不能靠继续替换字符来修补。

## 2. JSON 存在 SQL 字符串里，有两层转义

假设应用需要保存的 JSON 值包含：

```json
{
  "path": "C:\\new\\temp\\file",
  "line": "a\nb",
  "literal": "\\u4e2d"
}
```

这里既有路径里的字面反斜杠，也有 JSON 的换行转义，还有必须保留为文本的 `\u4e2d`。

当这段 JSON 再被放入 MySQL 字符串字面量时，会增加 SQL 层的编码。迁移过程应当是：

```text
MySQL 字符串字面量
  → 按源 SQL 模式解码一层
  → 得到原始 JSON 文本
  → 按目标数据库规则编码
  → 目标数据库读出相同的 JSON 文本
```

`decode_mysql_string` 只解码 SQL 层，`mysql_string_to_dm` 再用单引号双写编码目标字符串。它没有对内部 JSON 再做一次通用转义解码。

这也解释了为什么下面两种“修复”容易破坏数据：

- 删除所有反斜杠：路径、引号和 JSON 转义一起被破坏。
- 把全部文本按 Unicode 转义重新解码：原本应保留的字面文本可能被变成字符。

对应的测试同时比较解码后的文本和 JSON 解析结果。只比较 `json.loads` 的结果还不够，因为某些配置后续可能按原始文本参与摘要或差异计算。

源码还拒绝部分不支持的控制字符，而不是把它们悄悄放进迁移文件。这种失败应当带回源数据处理环节。

## 3. 替换语法之前，先保护字符串和注释

下面的示例并不包含两条语句：

```sql
INSERT INTO note(id, body)
VALUES (1, '正文里有分号 ;，还有 CREATE TABLE 和反引号 `x`');
```

如果按 `;` 直接切分，或全局替换反引号，处理的是业务正文。

转换器因此先做词法层的扫描：

- `quoted_end` 跳过引号片段，处理反斜杠和双写引号。
- `split_sql_chunks` 在识别的字符串、注释之外寻找语句分号。
- `split_top_level` 记录括号深度，在顶层切分字段或值列表。
- `transform_sql_code` 把代码片段交给语法转换，保护其中的字符串和注释。

有了这些边界，正则才适合用于有限的列定义、索引和已知语句形态。

这里仍然要承认能力范围。它是针对仓库已出现语法逐步实现的解析器，并没有完整覆盖 MySQL 语法。例如词法扫描对注释形式有自己的实现范围，不能未经测试就推广到所有合法 SQL 文本。

同样不能笼统地声称“任何未知语法都会报错”：部分明确支持的转换分支会拒绝未知形态，但 `convert_chunk` 最后仍有公共语法转换的回退路径。若要把工具扩展为面对任意外部输入的发布入口，需要补充顶层语句白名单与失败策略。

## 4. 幂等索引必须比较定义

迁移在中途失败后重试，可能遇到“前面的索引已经创建，后面的语句没成功”的状态。遇到已存在索引就忽略所有异常，容易把权限不足、定义错误等真正问题也吞掉。

`--idempotent-indexes` 采用另一种方式：先在目标模式的索引元数据里寻找等效结构，存在才跳过创建。

等效判断包含：

```text
当前 schema 与目标表
+ 索引处于 VALID 状态
+ 完整列数相同
+ 每个列的位置相同
+ 每个列的 ASC / DESC 方向相同
+ 创建唯一索引时，已有索引也必须唯一
```

例如希望创建 `(project_id, version, data_id)`，已有 `(project_id, version)` 不能当成完整等效。已有 `(version, project_id, data_id)` 也不能因为列集合相同而接受。

唯一性判断是有方向的：当前实现允许普通索引请求复用满足其他条件的唯一索引，但唯一索引请求不能被普通索引满足。表达式索引无法用这套直接字段比较覆盖，工具会拒绝为其生成这种保护块。

这个保护块支持的是顺序迁移失败后的重试。它使用“先查、再建”，本身没有提供并发创建索引的原子保证；也没有修改 Flyway 的迁移历史。发布编排和迁移记录仍是另外的责任。

## 5. 删除后插入，为什么只能用于受限种子

当前转换器对部分 `ON DUPLICATE KEY UPDATE` 种子，要求显式列清单且首列为数字 `id`，然后生成删除对应 ID、逐行插入的语句。

结构示意：

```sql
DELETE FROM "SEED" WHERE "ID" IN (101, 102);
INSERT INTO "SEED" ("ID", "NAME") VALUES (101, 'A');
INSERT INTO "SEED" ("ID", "NAME") VALUES (102, 'B');
```

这个方案容易生成，也容易重复得到给定的种子内容。但它不等价于任意业务 upsert。

一个反例就能看清差异：

```text
旧行：id=101, name=A, user_note=用户补充
新种子仅给出：id=101, name=B

只更新 name：
  user_note 保持原值

删除再插入：
  user_note 取默认值或 NULL，也可能违反约束
```

外键、删除触发器、审计记录和并发读取也会放大这个区别。首列为 ID 只检查了输入形状，没有证明“整行完全归种子管理”。

因此我会把适用条件写进交付要求：种子拥有哪些行与字段、是否存在用户补充数据、执行器如何组织事务、部分失败后怎样恢复。若不能满足，应使用明确的字段更新或经目标数据库验证的其他写入方案。

转换器还移除了源文件中的显式事务起止语句，交给目标迁移执行器处理。这进一步说明：生成文件里看不到 `COMMIT`，不能据此推断整个文件必然原子执行。

## 6. 结构检查需要一份可追溯的期望模型

与转换器相邻的 `mysql_migration_model.py` 解决另一个问题：仓库迁移最终期望什么列结构？

它按版本顺序离线重放已支持的列 DDL，记录类型、是否可空、默认值、原始定义、源文件和行号。创建、修改、重命名、删除都会改变这份模型。

这里的模型服务于结构检查，**不是当前转换器必须经过的统一中间表示**。两者共享部分词法处理，但不能把架构图画成一个实际上不存在的完整编译流水线。

几个实现选择值得保留：

- 按数字版本处理，避免把 `V2.10` 错排到 `V2.9` 前面。
- 检测归一化后重复的迁移版本。
- 保留列定义的 SQL 来源，不从 Java 字段类型反推数据库长度。
- 根 migration 目录的文件可以进入期望分析，但会产生警告：被分析不代表在默认扫描路径里被执行。
- 遇到不支持的列状态变更则报错，避免返回一份不完整却看似通过的结构。

例如检查发现某列长度不同，报告不应只写“数据库不一致”，还应指出哪份迁移、哪一行定义了期望值。这样问题才能进入评审和修复，而不是停留在脚本作者的解释里。

## 7. 我用哪些测试支撑这些结论

本次从固定提交提取转换器、结构模型和两个测试文件，在临时目录运行了 **46 项离线测试，全部通过**。没有连接 MySQL 或达梦。

测试选择覆盖：

| 场景 | 检查内容 |
| --- | --- |
| 嵌套 JSON、Windows 路径、中文与换行 | SQL 层转义后，文本与解析值保持一致 |
| 字符串中的 SQL、默认值中的关键字 | 不把数据误当成代码改写 |
| 混合 ALTER 与不支持的操作 | 操作顺序、字段属性与明确拒绝 |
| 索引重试保护 | 有序列、方向、唯一性及模式范围 |
| 定向转换 | 仅生成选定文件，并保留既有索引名称信息 |
| 结构离线重放 | 版本顺序、删除重建、来源行号与未知状态 |

测试脚本刻意没有执行依赖整套迁移目录的用例，也没有把字符串断言称为达梦执行验证。

下一层数据库验收，应使用脱敏的代表性数据，分别覆盖空库、旧版本库、半失败状态和重复执行。核对项目至少包括列定义、约束、关键值及应用读取结果；涉及 JSON 的字段，还要分别比对原始文本与应用解析。

这些是建议的交付验收项目，本文没有虚构一组客户环境的通过数据。

## 8. 把数据库适配做成可持续交付能力

手工修一份脚本可以解决一次发布，长期维护需要保留一条可重复验证的链：

```text
固定源迁移与工具版本
  → 定向生成候选 SQL
  → 离线语义测试
  → 目标数据库执行与值核对
  → 评审差异、记录发布证据
```

已发布迁移还涉及历史校验与既有环境状态，不能因转换器改进就批量重写。当前工具提供 `--files`，可以缩小生成范围，但它不会替团队解决历史迁移治理。

对技术负责人来说，这个方向的价值在于把兼容问题变成可定位、可重现、可验收的工程工作。下一次增加一种数据库或遇到一种新 SQL 形态时，团队能够说明新增了哪条规则、哪组反例证明它有效。
