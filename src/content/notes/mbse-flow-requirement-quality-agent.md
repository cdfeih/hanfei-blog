“控制通信中断后，系统应尽快进入安全状态。”

这是一条用于本文讨论的构造需求。读起来能够理解大意，但准备验证时，问题就出现了：“尽快”是多少时间？什么状态算安全？在哪种工况下判断？

让模型指出这些问题并不难。真正进入工程软件后，还需要知道它检查了哪个版本、依据什么规则，以及负责人修改需求后，这条发现是否仍然有效。

最近推进 MBSE Flow，我先把工程 AI 的一个阶段目标收敛到这里：用户能够检查一条需求，处理发现；需求提交新版本后，同一项检查能够自动发生。

目前，这条有限路径已有实现和自测记录，尚待独立复核。本文根据已提交代码与记录整理设计取舍。

## 先让一个技能真正可用

需求起草、影响分析、测试生成和方案设计都适合引入 AI，但同时铺开，会让最基本的问题被淹没：一次输出究竟能否成为用户愿意处理的工作项？

我选择从需求质量检查开始。它有明确输入，发现也容易回到原文核对。首个范围关注正文、可测试判据、已声明来源、适用条件和责任信息。缺少字段可以用确定性规则检查；措辞是否含糊、判据是否仍需澄清，则可以产生模型建议。

这里的“技能”包含一项任务的规则、适用范围、输入输出、提示版本和允许使用的能力。模型负责执行其中的判断。换模型、改提示或调整规则，都可能改变结果，因此这些版本需要被记录。

这类质量规则属于产品选择。它可以提示需求缺少可核对的判据，却不能仅凭一条建议，就宣布需求违反了 SysML 规范，更不能宣布设计已经通过工程验证。

## 先固定它看见了什么

检查开始时，用户可能正在编辑需求，另一位工程师也可能更新关联资料。如果模型读取正文时用一个版本，生成发现时又引用另一个版本，输出即使流畅，也很难复核。

当前实现先形成一份上下文包，关联模型提交、需求内容摘要、已声明来源版本、语言画像和技能版本，并记录读取项、缺口与预算。一次运行结束后，这份输入仍然可以与结果一起查看。

上下文还受权限约束。服务先确认用户能否访问项目和需求，再收集允许读取的内容；在实际调用模型之前，还会重新检查执行权限。上下文里的身份记录用于说明当时的输入，不能代替当前授权。

这也影响引用的处理方式。模型只能引用上下文中已有的来源。一个听起来专业、却无法对应到允许来源的编号，不能因为格式正确就进入正式发现。当前实现会校验输出结构、规则标识和来源引用，拒绝不符合契约的模型输出。

这些检查有各自的覆盖范围，仍需要反例验证。把一段资料标成“不可信数据”，本身并不能证明提示词注入已被彻底解决。

## 把发现做成用户能处理的对象

如果模型只返回几段文字，用户需要自己判断每句话指向哪里，也很难区分本次发现和上次发现。

我希望一条发现至少能回答：检查的是哪个对象和版本，使用了什么规则，问题依据在哪里，建议用户下一步确认什么。

下面是表达这种信息的构造示意，不是当前产品接口或原始模型输出：

```json
{
  "requirement": "REQ-DEMO-01",
  "checkedVersion": "v3",
  "rule": "可测试判据检查",
  "finding": "“尽快”缺少可核对的时间阈值",
  "basis": "本文构造的需求正文",
  "suggestion": "确认时间上限、起止事件与适用工况",
  "disposition": "待处理"
}
```

这里没有让模型替工程师填一个时间。缺少设计依据时，编出一个精确数字，往往比保留问题更危险。

当前发现项可以被确认、附理由驳回，或保留为待澄清；处理记录带有实际身份和版本。确认问题只改变发现的处置状态。用户要修改需求，仍然进入原来的草稿与服务端命令路径。

这样的分离让两种判断能够同时存在：我认可这条质量问题，但还没有决定如何修改设计；或者我驳回了某条建议，并留下适用条件。处置记录不应自动变成模型修改，也不应被直接推广为整个组织的新规则。

## 模型失败时，已经完成的检查怎么办

一次需求检查可能先产生确定性发现，再调用模型。假如模型服务超时，前面确认的“来源缺失”仍有依据，但整个检查显然没有全部完成。

当前实现保留已有发现，同时记录模型部分失败，并按实际情况呈现部分完成或失败。上下文超过预算、模型输出损坏、引用不合法，也有各自的诊断。

用户需要区分几种情况：

| 当前事实 | 可以如何理解 |
| --- | --- |
| 声明范围内的检查完成，没有发现 | 本次检查未发现问题，仍受规则和输入范围限制 |
| 部分检查完成，模型调用失败 | 已有发现可处理，其余部分尚未完成 |
| 输入在执行期间发生变化 | 结果保留为历史，需要检查新版本 |
| 尚未运行或因条件不足没有执行 | 当前没有足够的检查结果 |

把它们压成一个绿色图标，会使用户无法判断该修正文档、补充条件，还是重试服务。没有发现问题，也不能被扩展解释为需求在工程上已经得到验证。

## 从用户点击，走到需求提交自动触发

按需路径建立之后，下一步才是自动化。当前只接一种内部模型提交事件，从提交和父提交的快照中识别受支持需求的变化，再复用同一个技能执行入口。

事件与模型提交在同一事务中写入待投递记录，后续由持久任务处理。这样，浏览器不需要一直打开，也不依赖用户记得再点一次检查。自动任务生成的发现，仍进入同一个处理视图。

触发范围必须明确。画布移动位置不应启动需求质量检查；发现项更新也不能反复触发自身。自动策略需要授权用户显式启用，固定技能版本和预算，并记录启用水位。启用之前的历史，不会因为打开开关就被声称检查过。

当前实现也记录停用期间未处理的事件；历史回放尚未开放。重新启用策略，不能让那段空白悄悄消失。

这条路径带来的用户变化很小，却很具体：提交需求后，系统主动把待处理问题送回来。用户仍然负责判断发现与决定修改内容。

## 自动运行之后，要能解释重复与过期

事件可能重复投递，任务也可能在租约过期后被接管。因此，同一项变化需要稳定的去重依据，包含策略、提交、需求输入和技能版本，重复投递能够对应到原任务或回执。

去重并不意味着模型服务永远只被调用一次。重试、故障和接管仍可能带来额外调用，系统需要保存实际尝试与结果，限制失效尝试发布新的当前发现。

另一个常见问题是旧结果晚到。检查还没结束，需求已经进入新版本，旧结果就只能说明旧输入。当前实现保留历史运行，通过需求内容摘要和任务状态处理当前适用性；旧尝试不能凭借“最后完成”覆盖新结果。

撤权、停用、预算耗尽和提供方失败，也需要落到可见状态。后台任务失去执行资格之后，不能继续借用启用策略时的权限完成发布。

这部分已有自测与故障记录，但调度规模、完整安装恢复以及执行窗口内并发撤权等边界，还需要后续独立验证。一个小规模任务循环能够运行，不足以证明它已经适合任意工程负载。

## 给评测结果一个正确的分母

自动检查很容易出现一句含糊的汇报：“所有变更都检查了。”

这里至少有两个问题：符合当前策略的事件是否都得到处理，以及检查是否找到了应该发现的问题。前者是处理覆盖，后者才涉及漏报和误报。事件全部进入队列，也可能全部因为服务失败而没有完成。

因此，我会把接收、排队、完成、部分完成、失败和未处理原因分别记录，再看问题检出、错误引用、非法输出、越权、注入、延迟与费用。安全反例单独判断，不能用其他正常样例的平均分抵消。

当前评测使用可见的构造样例。它有助于建立回归，但不能称为独立盲测，也不能作为客户场景准确率。用户接受一条建议，同样不能直接算作模型判断正确；有些建议只是更符合当时的工作习惯。

输入门禁也会改变评测的含义。例如，如果一个缺少必填责任字段的案例先被提交校验拒绝，模型根本没有运行，这次结果证明的是服务端门禁，不能计入 AI 检出。设计评测时，需要先明确哪些合法输入能够到达被测环节。

这些口径会影响后续选择：是缺少上下文，需要补资料；还是规则有歧义，需要修订技能；或者任务恢复出了问题，应该先处理执行机制。只报一个综合分，很难指导研发。

## 这条小闭环之后

当前范围是一项需求质量技能和一种内部需求提交事件。它没有连接所有 CAD、代码仓库或里程碑，也没有自动完成工程方案、专业工具验证和发布。

对我来说，这一阶段最有用的积累，是让一次 AI 输出拥有明确输入、版本、处置和失败边界。它使后续增加技能时，有一条可以复用和验证的执行路径。

接下来需要让这条路径与资料版本、候选方案和实际工具结果逐步接合，同时保留人工入口。用户应该能沿着一条发现，知道它为什么出现、现在是否适用，以及自己处理之后究竟改变了什么。
