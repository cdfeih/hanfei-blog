在普通列表页面里，一个对象 ID 似乎足以定位数据。但建模平台允许同一个工程存在多个分支和版本，也可能引用其他工程。此时，“元素是谁”与“正在查看哪份元素状态”必须一起回答。

SE-MBSE 的版本化本地缓存提供了一个具体例子：缓存键不只包含数据 ID，还带有工程、分支与版本信息。

## 元素身份与视图身份

`AbstractVersionedCacheManager` 根据当前版本上下文生成键，基本结构可以概括为：

```text
缓存类型 : 工程 : 分支 : 版本 : 数据ID
```

其中草稿查询使用版本标记 0。这个标记表达可变工作状态，与已发布版本的语义不同。

用一个虚构例子说明：同一元素在分支 A 的草稿里名称是“控制单元”，在某个历史版本里名称是“控制模块”。如果键只有元素 ID，最后一次写入缓存的名称就可能污染另一种视图。

给键补足身份维度，是保证结果正确的条件，而非单纯为了让 key 更长。

## 跨工程引用不能偷偷使用当前上下文

当前实现区分本工程与导入工程。对于外部工程，它从 `ProjectImport` 查找被引入的工程、分支和版本，再生成对应缓存键。找不到引用或引用尚未关联时，返回空键，不继续触发依赖数据加载。

这个处理值得保留为明确语义：引用尚未解析，不等于可以任选一个默认版本。

| 情况 | 合理处理方向 |
| --- | --- |
| 本工程元素 | 使用当前查看上下文 |
| 已解析的导入工程元素 | 使用引用指定的分支与版本 |
| 未关联引用 | 保留未解析状态，避免猜测数据来源 |

是否允许自动补关联属于业务规则，不能让缓存层为了命中率擅自决定。

## 缓存结果也有所有权

`ElementCacheManager` 使用本地 LoadingCache 保存元素视图。单次读取后，它通过 `BeanCopierUtils.copyProperties` 返回复制结果；另一个读取方法还会为返回值补充可读的限定名路径。

这表明调用方拿到的对象可能继续被加工。如果直接把共享缓存中的同一个可变对象返回出去，某个页面的补充字段就可能影响另一个调用方。

不过，看到 copy 调用并不能自动证明所有嵌套对象都已深复制。若视图中包含列表或可变子对象，还应核对复制工具的实际语义。

一个有效测试是：读取对象并修改其嵌套字段，再次读取，观察第二次结果是否受到影响。

## 空结果缓存需要失效策略

当前缓存将值包在 Optional 中，因此“确实没有这个元素”也可以被缓存。这有助于避免重复查询不存在的数据，但随之产生一个问题：元素后来创建了，原来的空结果如何失效？

缓存容量和过期时间只能提供兜底，不能替代业务变更后的失效通知。对于草稿版本，数据持续变化；对于历史版本，也要先确认系统是否真正保证其不可变，再决定缓存多久。

当前类提供单项失效、整体清空和批量预热入口。是否覆盖了所有变更路径，需要继续核对对应事件与调用者，不能仅凭这些方法存在就宣称一致性闭环已经完成。

## 验证应覆盖“同 ID、不同世界”

比随机读取几个元素更有价值的场景，是让相同 dataId 出现在不同上下文：切换分支、查看历史版本、跨工程引用、未解析引用、先查不存在再创建。

检查结果时同时记录上下文与缓存键。如果键正确而数据仍错误，再检查加载函数；如果键已经混淆，就没有必要先怀疑序列化或渲染层。

缓存设计最重要的第一步，是准确描述数据的身份。容量、淘汰与命中率，都应该建立在这个前提上。
