“给我读取这个元素。”

在单版本演示系统里，一个元素 ID 可能就够了。到了真实项目，同一个元素可能已经改名、换类型、调整关系，甚至在某个版本中被删除。

这时，读取请求还缺少一个条件：你要的是哪一次提交所确定的状态？

这一篇依据 Systems Modeling API and Services 1.0，文档号 `formal/2026-03-04`。它是与 SysML 2.0 配套的独立规范，不能因为语言版本是 2.0，就把 API 的正式版本也写成 2.0。[OMG API 官方目录](https://www.omg.org/spec/SystemsModelingAPI/1.0)

## 1. 先分开稳定身份和版本内容

规范的项目数据版本模型区分 `DataIdentity` 与 `DataVersion`：同一数据的不同版本共享身份，而版本记录具有自己的标识和内容。`Commit` 组织版本变化，`Branch.head` 指向分支当前提交。[API 1.0 §7.1.2](https://www.omg.org/spec/SystemsModelingAPI/1.0/PDF#page=33)

用一个原创的数据时间线来理解：

| 提交 | 元素稳定身份 | 名称 | 响应时间 |
| --- | --- | --- | --- |
| C1 | E1 | coolingUnit | 0.10 秒 |
| C2 | E1 | primaryCoolingUnit | 0.11 秒 |
| C3 | E1 | 当前提交中不存在 | — |

表中的 `C1`、`E1` 是解释用代号，不是标准 API 真实 UUID 值，也不是响应 JSON。

重命名之后，E1 仍然代表同一个元素身份；C3 中不存在，也不意味着 C1 的历史证据应该被擦掉。

这个区分影响的不只是数据库设计，还影响差异比较、外部引用和测试报告的可追溯性。

## 2. 路由已经把版本上下文放到了显式位置

OMG 发布的 REST/OpenAPI 文件包含这样的元素读取路径：

```http
GET /projects/{projectId}/commits/{commitId}/elements/{elementId}
```

分支读取则有：

```http
GET /projects/{projectId}/branches/{branchId}
```

以上是路径模板，参数需要替换为有效标识。[官方 OpenAPI JSON](https://www.omg.org/spec/SystemsModelingAPI/20250201/OpenAPI.json)

对调用方来说，显式 `commitId` 至少让一句话变得完整：“我要读取项目 P 在提交 C 中的元素 E。”

它仍然没有自动解决授权、网络错误或模型完整性，但避免了把“当前到底是哪版”藏在一个容易变化的服务端默认值里。

## 3. 用一次分支推进观察读取漂移

假设页面需要读取结构树，再读取树中元素的属性：

```text
T1：读取分支 main，得到 head = C1
T2：另一位用户提交修改，main.head 变成 C2
T3：读取结构树
T4：读取元素属性
```

如果 T3 和 T4 都重新请求“最新状态”，两个结果可能来自不同提交。界面看起来像一份完整模型，实际上拼接了两个时刻的数据。

我的客户端建议是：一次需要一致视图的读取过程，先解析分支到某个提交，再把这个提交用于相关读取。

```text
解析 main → C1
读取 tree(project=P, commit=C1)
读取 element(project=P, commit=C1, element=E1)
```

当用户需要刷新到最新状态时，再重新解析分支。

这是基于版本模型提出的读取策略，不是声称所有 API 请求会自动形成数据库快照事务。跨项目依赖也需要各自固定版本，不能只固定主项目就宣称整个依赖闭包一致。

## 4. 缓存键必须与读取语义一致

下面这个缓存键会把不同提交混在一起：

```js
const key = elementId;
```

即使换成分支 ID，也不一定解决问题。分支头会推进，同一分支名不等于固定内容。

对固定提交读取，我会先考虑这样的键：

```js
const key = JSON.stringify({
  projectId,
  commitId,
  elementId,
  projection,
  accessScope,
});
```

其中前三项来自读取身份；`projection` 表示本产品选择的字段或展开方式，`accessScope` 表示可能影响结果的权限上下文。后两项是实现建议，不是标准规定的缓存字段。

如果产品有多个后端实例或租户，同样还要考虑服务来源与租户隔离。如果权限会改变，还必须决定失效策略。不能因为模型提交不可变，就假设用户可见结果也永远不变。

这类问题用单用户、单工程数据很难测出来。我会专门构造两个提交中同一元素内容不同的情况，确认缓存没有串版。

## 5. Commit、Branch、Tag 的产品含义不同

标准区分了这些记录的可变性：正常用户操作中，Commit 不可修改和删除；Branch 可变；Tag 指向的提交不可修改，但 Tag 可以删除。管理性修复是另外的边界。[API 1.0 §7.1.2](https://www.omg.org/spec/SystemsModelingAPI/1.0/PDF#page=34)

从产品设计上，我会把它们分别解释为：

- Commit：用于回溯的历史事实；
- Branch：持续推进的工作入口；
- Tag：标记某个关心的提交。

这不是要求后端必须用 Git 存储。接口语义和物理实现是两件事。

如果本地系统允许直接改写已发布模型，再让同一个“版本号”继续代表它，就需要认真考虑怎样映射为标准提交。仅把内部表中的 `versionId` 字段重命名为 `commitId`，并不会自动获得相同语义。

## 6. 删除和合并，先讨论事实再讨论按钮

删除一个元素时，产品通常希望当前树里不再显示它；审计人员则希望仍能读取旧提交。

这两种需求并不矛盾。我的存储评估会要求明确：删除如何影响当前状态，旧状态怎样重建，关系端点失效怎样检测，外部引用还能否解释。

合并也类似。两条分支都改了 E1，一条改类型，一条改与该类型相关的属性。即使文本层面没有碰到同一行，也可能产生语义冲突。

因此，我不会把“版本图可以有多个父提交”直接等同于“系统已经具备自动语义合并”。一个产品仍需设计冲突判定、解决策略和合并后的模型检查。

关于合并规则，规范 §7.1.2 提供进一步约束；本文不复述完整算法。这里关注的是实现时必须回答的问题。

## 7. 标准 API 与 MCP 应怎样协作

我们已经在 SE-MBSE 中讨论过 MCP 工具。两种接口容易被混称为“给 AI 用的模型 API”，但它们服务的契约不同。

对于适配层，我会这样划分：

```text
用户目标
  → MCP 领域工具：创建、检查、解释和恢复
  → 受控业务服务
  → 标准模型访问或交换接口
  → 模型及其版本事实
```

这是架构建议，不是在宣称当前 SE-MBSE 已通过 Systems Modeling API 符合性测试。

尤其要避免两种 ID 混用：

- MCP 的 `operationId` 标识一次工具操作及其回执；
- 标准 API 的 `commitId` 标识模型版本历史中的提交。

一次工具操作可能没有产生提交，也可能涉及多步领域动作。二者可以建立关联，但不能因为都叫“操作记录”就共用同一个含义。

同样，内部 Long ID 和标准 API 使用的标识形式之间，需要明确映射。不能简单把 Long 转成字符串就宣称完整遵循标准的身份契约。

## 8. 做一个能说明问题的适配验证

如果要给既有平台增加标准 API，我会优先验证一个很小的场景：

1. 创建项目并取得默认分支；
2. 提交一个元素，记录元素身份和提交标识；
3. 修改名称，形成下一次提交；
4. 分别读取两个提交，确认旧名称和新名称都可得到；
5. 删除当前元素，再检查历史读取；
6. 让两个调用者同时推进分支，检查并发语义；
7. 按声明支持的服务范围执行规范的相应符合性测试。

前六步是我的最小回归场景；第七步不能被“几个接口返回 200”替代。规范第 2 章列出不同符合性范围，不能把只读子集包装成完整服务实现。[API 1.0 第 2 章](https://www.omg.org/spec/SystemsModelingAPI/1.0/PDF#page=16)

## 9. 标准带来的价值，是让问题不能继续隐含

模型平台真正难的，往往不是序列化出一份 JSON，而是解释这份 JSON 代表哪个项目、哪次提交、哪个身份，以及它和上一次结果之间是什么关系。

把这些问题放到接口契约中，缓存、追溯、验证证据和 AI 操作才能共享清楚的版本坐标。
