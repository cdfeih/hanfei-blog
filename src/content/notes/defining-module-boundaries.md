一个复杂平台通常同时包含界面交互、业务规则、数据存储与外部系统集成。如果只按页面划分模块，同一条规则可能出现在多个地方；如果只按技术层划分，一次业务变化又可能需要跨越很多目录。

模块边界要回答一个具体问题：当某件事发生变化时，谁应该负责理解它、实现它，并验证它？

## 先找变化的原因

以建模编辑器中的"重命名元素"为例，输入框样式、命名约束、存储协议和协同通知，都可能随着不同原因发生变化。

| 变化 | 主要关注点 | 建议归属 |
| --- | --- | --- |
| 输入框增加即时提示 | 用户反馈与交互 | 界面层 |
| 同一命名空间禁止重名 | 命名规则的一致性 | 领域规则 |
| 更新后触发关联操作 | 步骤编排与失败处理 | 应用层 |
| 存储或通信方式改变 | 外部依赖的适配 | 基础设施 |

把变化的原因列出来，比立即画一张庞大的模块图更容易发现问题。同一个规则如果需要在不同入口反复实现，就是值得检查的信号。

## 让规则有明确的归属

用户可能通过属性面板、模型树或导入功能触发重命名。界面可以提供提前校验，但最终的业务约束需要有统一的执行入口。

> 一个模块的边界，应当让团队清楚：规则在哪里，以及修改它需要承担什么责任。

这并不意味着每一层都必须成为一个独立部署的服务。代码职责和部署形态可以分别决策。对于需要频繁一起交付的功能，清晰的模块化结构往往是一个更容易验证的起点。

### 依赖方向的建议

建议依赖方向：界面调用应用层，应用层调用领域规则；基础设施通过接口接入应用层。图 1 是简化的职责划分示意。

- **界面交互**：提交用户意图
- **应用编排**：调用领域规则
- **领域规则**：维护业务约束

## 把边界写成可讨论的契约

讨论模块时，除了命名和目录，更需要说明输入、输出、错误和副作用。下面用一个示意接口表达重命名操作的边界：

```ts title="示意接口"
type RenameElementCommand = {
  elementId: string;
  nextName: string;
  expectedVersion: number;
};

type RenameResult =
  | { ok: true; version: number }
  | { ok: false; reason: 'conflict' | 'invalid-name' };

// 约定操作结果；具体事务与通知策略另行定义。
interface RenameElement {
  execute(command: RenameElementCommand): Promise<RenameResult>;
}
```

版本字段用于表达调用者看到的数据版本。实现时仍需要明确检查与更新的原子性、冲突时的反馈方式，以及操作成功与消息通知之间的关系。接口能够帮助暴露这些问题，但无法自动解决它们。

## 用一次真实变化验证设计

选择一个跨入口的需求，沿着实际执行路径检查边界：

1. **规则是否一致**：从模型树和属性面板操作，是否遵守相同的命名约束？
2. **变化是否集中**：调整约束时，是否需要同步修改多个副本？
3. **失败是否可解释**：当版本冲突或持久化失败时，用户能否理解结果？
4. **协作是否清楚**：谁修改契约，谁验证调用方，谁负责集成？

这些检查可以转化为验收场景。架构评审也就有了具体依据：检查规则和操作结果，记录跨模块修改的范围，再决定是否调整边界。

## 留下决策，也留下适用条件

每个边界都会带来代价。更明确的接口可能增加转换代码；更细的模块可能增加协作成本。技术方案应当记录选择的原因、接受的代价，以及什么时候需要重新评估。

对于技术负责人，架构图、模块职责和团队任务应该能够相互对应。这份对应关系有助于让设计进入日常开发、评审和交付。

> 从一个具体变化出发，让边界经得起实现与协作的检验。
