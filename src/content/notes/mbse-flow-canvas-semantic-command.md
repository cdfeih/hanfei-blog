最近推进 MBSE Flow 时，我重新拆解了一个看起来很小的交互：用户从工具箱拖一个部件到画布上。

站在使用者这边，这个动作应当直接、自然：拖进去，起个名字，填写参数，继续设计。站在研发这边，它同时触及对象身份、类型、归属、权限、版本与布局。如果这些问题没有共同依据，画布、参数表和 AI 就容易各自维护一份设计。

在[之前的总体方案](/notes/mbse-flow-design/)里，我讨论过语义、版本和证据的边界。这篇文章把范围缩到一次操作，看看这些边界如何进入日常交互。文中的命令和数据均为设计示意；现有项目仍是有限能力的研发版本，本文没有重新运行产品测试，也不据此声明完整标准支持。

## 先说清楚这次拖入表达什么

工具箱里的一个“泵”，可能有几种含义：创建一种可复用的泵类型，在当前冷却回路中添加一个泵的使用，或者把模型里已有的泵显示到当前图中。

这三件事需要不同的操作结果。

| 用户意图 | 模型需要记录什么 | 当前视图需要记录什么 |
| --- | --- | --- |
| 定义一种泵 | 类型及其特征、约束 | 类型的呈现位置 |
| 在回路中添加循环泵 | 特定上下文中的使用及类型关联 | 新对象的图元 |
| 把已有循环泵放到另一张图 | 保留原语义对象 | 新增一个指向它的呈现 |

如果“添加已有对象”实际复制了模型对象，两张图会从此独立变化。用户以为自己在查看同一台循环泵，系统里却出现了两个不同的设计角色。这个错误很难靠调整节点颜色或刷新列表修好。

因此，我希望工具箱在操作发生前就能明确意图：创建类型、创建使用、显示已有对象。界面不必把元模型名全部展示出来，但需要让人知道自己正在新增设计内容，还是增加一个观察它的位置。

## 定义和使用，影响的是修改范围

[SysML 2.0 的定义与使用机制](https://www.omg.org/spec/SysML/2.0/Language/PDF#page=63)为这类区分提供了语义基础：定义描述某一类元素，使用表达它在特定上下文中的应用。

例如，“泵”可以是一种部件定义；“冷却回路中的循环泵”则是在该回路上下文中的部件使用。这里的使用也不直接等于一台已经制造、带有设备编号的实物。

这个区分决定属性面板中的修改应落在哪里。更改通用泵类型的特征，与修改当前回路中循环泵的具体约束，具有不同的作用范围。界面应说明正在编辑类型还是当前使用，也应说明一个值来自哪里。

继承的默认值、当前上下文中的重定义和固定绑定，还要继续区分。让用户看到一个可输入的单元格之前，服务端必须知道这个属性是否允许在这里修改。单元格能够输入，并不意味着这次修改具有合法的语言语义。

这些规则需要来自所采用的语言和能力范围。对于尚未支持的重定义或表达式，产品应给出具体诊断，保留用户输入供后续处理。

## 图元和语义对象需要分别保存

一次创建可以同时产生语义对象和图形呈现，但它们具有不同的生命周期。

语义对象记录类型、归属、属性与关系；呈现记录这张图中对象的位置、尺寸、折叠和标签安排。一个语义对象可以在多张图中出现，每个呈现都引用同一个对象身份。

这样，拖动循环泵的位置只需要保存布局。通过参数表修改循环泵的设计属性，则需要产生模型变化。两者都要可恢复，但不应互相制造无关的语义变更。

删除也必须表达清楚。“从此图移除”只删除呈现；“从模型删除”还可能影响连接、需求关联以及其他图中的呈现。后者需要展示影响范围并经过相应命令检查。把它们都放进一个没有说明的删除按钮，会让用户承担理解内部存储的风险。

在当前受限实现中，布局和模型已采用分开的保存路径；这项基础仍需要和更多编辑动作一起验证。标准图形记法、撤销重做及复杂视图行为，也有各自的实现工作，不能由一张可拖动的画布代替。

## 稳定身份让多视图指向同一件事

循环泵从“泵一”改名为“主循环泵”，又被移动到另一层结构中，用户通常希望之前的关联仍能找到它。

因此，我会把对象身份与显示名称、当前路径和数组位置分开。名称用于交流与查找，路径表达当前结构；它们变化时，对象身份可以继续保留。内容版本则说明这个对象在某次提交中是什么样子。

参数表、对象树和画布据此共享同一份语义对象。视图可以有自己的选择、滚动和展开状态，但提交后展示的对象内容应来自同一个明确模型版本。

这还带来一个容易忽略的判断：把已保存的图关闭再打开，并不能单独证明身份保持正确。至少需要检查更名后的引用、另一视图中的同一对象，以及历史版本能否读回。界面看起来相似，底层可能已经重新创建了对象。

## 服务端接收明确的修改意图

在客户端，我更愿意先组织一条可解释的建模意图，再交给服务端检查，而不是让图形组件决定最终模型结构。

下面只说明命令应携带哪类信息，字段和值均为示意，**不是当前接口、可直接调用的请求，也不是 OMG 标准交换格式**：

```json
{
  "intent": "createPartUsage",
  "baseRevision": "model-r12",
  "ownerId": "cooling-loop",
  "typeId": "pump-type",
  "name": "circulationPump"
}
```

这里明确了用户依据哪个版本、把什么类型的使用放进哪个上下文。实际身份来自服务端认证，不能靠这段内容自行指定权限。

服务端随后核对基准、归属和引用，构造候选，执行承诺范围内的语义校验，再决定能否形成有效提交。当前项目已围绕统一语义提交组织有限的对象编辑；更完整的合并、影响和审阅流程仍需继续集成。

图形、表格、文本与 AI 都应进入这条共同路径。它们可以采用不同交互，却不能分别拥有另一套“什么模型可以保存”的解释。尤其是 AI，生成了一段看似完整的修改，也仍需接受相同的类型、权限与版本检查。

## 草稿让操作连续，冲突让前提可见

服务端验证需要时间，用户也可能只填了一半参数。此时界面仍然需要保存工作进度。

我会让未完成的对象先以明确草稿状态存在：用户能继续编辑、关闭后找回，并知道它尚未进入有效模型。文本解析失败、引用缺失和未支持语义，应定位到具体对象或输入位置，给出修正入口。保存草稿与提交模型分别表达结果。

多人操作还会改变提交的前提。用户基于版本十二添加循环泵时，另一位工程师可能已经调整了回路结构。如果服务端返回版本冲突，界面需要保留本次输入，同时展示现在的基准和相关变化。

自动刷新并清空表单会丢失工作；把旧输入无条件重发，又可能把刚出现的变化覆盖掉。对于需要重新确认的冲突，应让用户基于新状态重新准备提交，并能看到实际版本与预期版本。权限不足、版本冲突和语义拒绝各有自己的原因，界面应提供相应的处理方式。

## 我会怎样验收这次拖入

我希望从这个小动作同时检验几件事：创建的到底是预期上下文中的使用，重开后是否仍有同一身份，另一视图能否读到相同内容，移动位置是否只改变布局，以及冲突和非法输入是否保住了草稿。

还需要反过来验证拒绝路径。连接到尚未支持的端类型、导入无法理解的关系或遇到未知单位时，系统应指出未覆盖内容，不能静默丢弃之后返回一个完整成功。对于建模工具，拒绝得清楚也是产品能力的一部分。

最终我希望用户感受到的仍然是一次自然的拖拽。底层的身份、语义和提交检查为这个动作提供共同依据，专业细节则在需要解释或纠正时出现。画布因此能够进入工程工作流：人们在上面修改的是有明确含义、能够被其他视图和验证过程继续使用的设计。
