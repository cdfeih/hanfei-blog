“控制器连接到了需求，追踪矩阵已经全绿。”

这句话可能表示需求已经分配了责任对象，也可能表示模型声明该对象满足要求。但它还没有回答：测了什么，针对哪个版本，结果从哪里来？

在工程平台里，如果把这些事情压成一个“已满足”字段，早期演示会很顺滑，后续评审却会不断追问证据。本篇用一个响应时间要求，把这些层次拆开。

依据为 SysML 2.0 正式语言规范，文档号 `formal/2026-03-02`。本文给出的工作流和证据字段是设计建议，不是 OMG 对数据库或界面的指定实现。

## 1. 三个问题分别由什么回答

标准将 requirement 建立在约束之上：假设成立时，要求应成立。`satisfy` 表达绑定到满足者的满足断言；verification case 则以验证目标和 verdict 组织验证。[SysML 2.0 §7.21.2、§7.21.4、§7.24.2](https://www.omg.org/spec/SysML/2.0/Language/PDF#page=165)

在项目讨论中，我会把它们翻译成三个不同的问题：

| 问题 | 我们希望模型表达什么 |
| --- | --- |
| 要求是什么 | 在哪些条件下，什么对象必须满足什么条件 |
| 哪个设计承担这个要求 | 满足断言绑定到哪个具体角色 |
| 凭什么接受这个断言 | 验证活动、输入、结果及相应证据 |

第三项不能由第二项的存在自动推出。一个断言可以等待证明，也可能被后续证据推翻。

## 2. 从一句自然语言要求开始

假设我们要表达：

> 冷却单元的启动响应时间不超过 0.12 秒。

先写一个小模型，明确对象、量值和阈值：

```text
package CoolingRequirements {
    private import ISQ::*;
    private import SI::*;

    part def CoolingUnit {
        attribute responseTime : TimeValue;
    }

    requirement def StartResponse {
        subject unit : CoolingUnit;
        attribute maxResponse : TimeValue;
        assume constraint { maxResponse > 0[s] }
        require constraint {
            unit.responseTime <= maxResponse
        }
    }

    requirement responseLimit : StartResponse {
        attribute :>> maxResponse = 0.12[s];
    }
}
```

这是本文原创的教学示例。它依赖标准量值与单位库，但还没有建模采样过程、时钟误差和启动条件，不应被当成可直接验收的完整需求。

为什么愿意先写得这么小？因为每增加一个概念，都应知道它解决了哪个歧义：

- `subject` 指明需求针对的对象；
- 时间类型和单位让数字有物理意义；
- 阈值成为可绑定的参数；
- 约束表达允许检查的关系。

原来一句容易理解的话，现在至少有了可追踪的结构。

## 3. assume/require 最容易被误读的地方

为了分析逻辑，先把本例简写成：

```text
A：maxResponse > 0
R：responseTime <= maxResponse
需求条件：A ⇒ R
```

这只是命题逻辑说明，不是另一份 SysML 代码。

| A | R | A ⇒ R | 这能否直接当作工程验收结论 |
| --- | --- | --- | --- |
| 真 | 真 | 真 | 仍需确认数据和条件有效 |
| 真 | 假 | 假 | 条件成立时未达到要求 |
| 假 | 真 | 真 | 不在已声明假设内 |
| 假 | 假 | 真 | 同样不能证明规定工况下达标 |

假设不成立时，蕴含在逻辑上为真。这里没有标准“出错”，问题是人把逻辑求值误当成“设备已被充分验证”。

例如配置错误把 `maxResponse` 设成负数。如果平台仅显示整个蕴含的布尔结果，就可能让配置错误看起来像检查通过。

我会把这两个问题分开处理：

1. 阈值配置是否合法，单独检查；
2. 需求的适用假设是否得到证据支持，单独展示。

这样不会让“参数坏了”通过一个假前提悄悄消失。

同样，不要为了让模型看起来成立，把所有难以满足的情况都塞进 assume。假设代表适用边界，需要由项目上下文承担责任。

## 4. 添加 satisfy，表达的是哪一个事实

继续在同一个包中添加：

```text
part candidate : CoolingUnit {
    attribute :>> responseTime = 0.10[s];
}

satisfy responseLimit by candidate;
```

这时，设计模型声明 candidate 满足 responseLimit，并提供了一个用于本例比较的响应时间值。

但这个 `0.10[s]` 从哪里来？

- 供应商手册中的典型值？
- 仿真输出？
- 一次单机测试？
- 高温、低电压情况下多次试验的最大值？

在数学比较中，这几种来源可能都是同一个数字；在工程评审里，它们支持的结论不同。

所以我不会让“创建 satisfy 关系”同时执行“验证状态改为通过”。前者记录模型声明，后者应由明确的验证流程和结果支持。

## 5. Verification case 不只是一条 verify 连线

下面是一个验证计划骨架，仍然放在 `CoolingRequirements` 包内：

```text
verification def StartResponseEvidence {
    subject unit : CoolingUnit;
    objective {
        verify responseLimit;
    }
}
```

它表达验证目标，但没有定义如何触发启动、如何采集响应时间、如何处理误差和如何得出结果。本文没有把它包装成“可执行测试”。

如果要真正实现这个验证，我会补全一条明确的数据链：

```text
固定被测版本
  → 建立规定工况
  → 发出启动信号
  → 采集起止时间
  → 检查测量有效性
  → 计算响应时间与不确定度
  → 作出判定
  → 保存结果和证据引用
```

其中“检查测量有效性”必须在阈值比较之前。没有采到结束事件时，不能用默认值 0 秒代替，否则最严重的数据缺失反而会产生最漂亮的结果。

## 6. 四种 verdict 怎样帮助产品避免说错话

标准给出的验证 verdict 包括 `pass`、`fail`、`inconclusive` 和 `error`。[SysML 2.0 §7.24.1](https://www.omg.org/spec/SysML/2.0/Language/PDF#page=173)

对这次响应时间验证，我会采用如下判定约定。注意，以下具体映射是本文的验证策略示例，不是标准对每种测量故障的强制分类：

| 观察到的情况 | 本例判定策略 | 界面应该解释什么 |
| --- | --- | --- |
| 有效测量区间整体不超过阈值 | pass | 哪次测量支持这个结果 |
| 有效测量区间整体超过阈值 | fail | 超出多少，条件是什么 |
| 测量区间跨越阈值 | inconclusive | 现有精度不足以作出决定 |
| 测量程序异常、采集链故障 | error | 验证过程自身未正常完成 |

例如测得 `0.119 ± 0.003` 秒，阈值是 `0.120` 秒。若采用“整个测量区间都在阈值内才通过”的保守策略，区间上端为 `0.122` 秒，就不能仅比较中心值后宣布通过。

其他领域可以采用不同的统计判据，但必须在验证方案里说清楚。SysML 提供表达结构，领域方法仍然需要工程团队负责。

## 7. 证据应绑定版本，而不只绑定名称

假设控制算法升级后，需求名称和设备名称都没改，原测试报告也仍然存在。旧报告是否证明新算法满足响应要求？

不能仅凭“名字相同”作出判断。

我建议验证记录至少能够追溯：

- 被验证的模型对象及其版本上下文；
- 需求版本与参数；
- 验证方法、工具和配置；
- 输入工况、原始记录和处理结果；
- verdict 及形成该结论的理由。

这些字段不必全部放在同一张表，也不必全部存进 SysML 文本。可以通过稳定引用关联外部数据，但引用必须能找回当时的对象与内容。

模型更新后，平台还需要区分“旧结论仍可复用”“需重新评估”“明确失效”。直接把全部绿色状态复制到新版本，会隐藏真正的影响分析工作。

## 8. 用追踪矩阵回答对的问题

追踪矩阵很适合展示缺口，但每个颜色必须有明确含义。

我会分别统计：

1. 有没有满足断言；
2. 有没有验证计划；
3. 有没有执行记录；
4. 当前版本有没有可接受证据。

这四个覆盖率可能完全不同。一个系统可以实现 100% 关系覆盖，却没有任何当前版本的试验结果。

把这些状态分开，团队就知道下一步是补建模、补计划、执行试验，还是重新评估证据。标准解读因此能直接影响工作流设计，而不只是增加几个专业词。
