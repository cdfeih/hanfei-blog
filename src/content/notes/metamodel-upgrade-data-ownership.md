建模平台支持“元模型发版”，只完成了演进的一半。另一半发生在已经建好、已经被用户修改过的工程里。

设想一次看似很小的更新：框架里增加一个分组，调整一条导入关系的可见性。新建工程能看到变化，老工程执行升级后却仍然显示旧配置。元素树没有报错，版本号也向前走了，为什么结果不对？

在 SE-MBSE 这一轮实现中，问题出在升级对象的范围：元素的增删改移进入了差异计算，挂在已有元素上的分组配置和导入关系却没有进入同步。新增节点会随克隆带上关联数据，未新增的节点反而一直保留建工程时的状态。

我认为，这个案例最值得讨论的是：**一套模板被复制到用户工程以后，哪些数据仍由模板管理，哪些已经属于用户？** 这个问题没有回答清楚，升级算法就无法决定该覆盖、保留还是提示冲突。

## 1. 元素没变化，不代表元素承载的配置没变化

先看一个简化例子，编号仅用于说明：

```text
元模型目标版                         存量工程
包 A：100                           包 A 的工程副本：900
  分组 G：visible=false               分组 G：visible=true
  导入 I：visibility=private          导入 I：visibility=public

元素层面：A 配对成功，无新增、无移动
关联数据：分组与导入均有变化
```

如果升级只检查包 A 的名称、类型和位置，就会得到“没有需要处理的变化”。更隐蔽的是，树读取侧优先使用工程本地配置：旧数据仍然合法存在，因此也不会自动回退到元模型的新配置。

这给平台设计提出一个要求：差异清单必须覆盖**功能的完整数据集合**。对于这个场景，至少包括元素、分组头、分组明细和导入关系。数据库表是否分开存放，不应决定某类数据是否参加升级。

当然，完整不等于把所有关联表一律覆盖。下一步要先区分所有权。

## 2. 同样是复制来的数据，同步策略可以不同

当前项目中，两类数据的编辑入口不同：

| 数据 | 工程侧行为 | 本轮采用的同步方式 |
| --- | --- | --- |
| 分组显示配置 | 建模工程没有直接编辑入口 | 对齐元模型目标版 |
| 包的导入关系 | 用户可以添加、修改、删除 | 用来源标记配对，再区分用户是否修改 |
| 标准库自动导入 | 由专门的读时对账逻辑维护 | 排除在本轮升级同步之外 |

分组配置可以作为框架在工程里的投影。导入关系则混合了框架默认值和用户意图，两者需要不同规则。

标准库自动行的排除也很重要。如果升级服务和标准库对账服务都认为自己拥有这批数据，就会出现两个写入者反复修正对方的结果。当前实现通过 `importedStdLibUri` 与遗留的 `STDLIB:` 分类排除这些行。

这比抽象出一个“通用同步器”更早：先确定写入责任，再讨论复用算法。

## 3. 跨工程对齐，先解决身份映射

元模型中的 `dataId=100`，在工程中可能已经变成 `dataId=900`。直接按数据库 ID 比较，会把同一个业务节点误判成删除加新增。

升级主流程因此合并两份映射：

```java
// 源码节选：源侧元素 ID -> 工程侧元素 ID
Map<Long, Long> sourceToCurrentMap =
    new HashMap<>(diff.getMatchedDataIdMap());
sourceToTargetDataIdMap.forEach(
    (sourceId, task) -> sourceToCurrentMap.put(sourceId, task.getDataId())
);
```

第一份覆盖已经配对的元素，第二份覆盖本次新增并克隆的元素。关联数据同步放在固定结构处理之后，才能拿到新宿主的工程侧 ID。

但“有映射”不意味着所有引用都应该重写：

- 导入目标在映射集里：替换为工程侧元素 ID，工程 ID 同时切换。
- 导入分类为 `META_CURRENT`：按当前实现保留元素 ID，将工程 ID 指向目标工程。
- 引用外部工程：保留外部目标。

分组明细里的 `definitionDataId`、`definitionDataPid` 又采用另一套口径：保持定义引用，仅重映射宿主与分组 ID，与已有克隆及读取匹配逻辑一致。

**标识长得相似，不代表语义相同。** 代码生成器很容易统一字段类型，升级服务却必须知道每一个标识指向哪个身份空间。

## 4. 分组对齐：无变化就不写入

`rebuildByMapping` 分两层建立业务键：

```text
分组头：
  (映射后的 ownerId, groupName)

分组明细：
  (映射后的 ownerId, 映射后的 groupDataId,
   elementType, definitionDataId, definitionDataPid)
```

先配对分组头，再用分组 ID 映射配对明细。配对成功且内容一致时，保留原来的行与 `dataId`；内容不同则替换；源侧已经不存在的目标行进入删除集合。

这里有一个容易遗漏的连锁关系：分组头替换后拿到了新 ID，明细必须重挂到新分组。不能只比较明细里的排序和可见性，然后认定“不需要更新”。

这种实现还刻意保留“没有变化”的状态：

```text
插入分组 = 0
删除分组 = 0
插入明细 = 0
删除明细 = 0
  → 直接返回
  → 不触发这一路的树投影缓存失效
```

在有版本记录的系统里，最终查询结果相同只是幂等性的一部分。每次重试都删掉再插入，会制造新 ID、版本噪声和缓存抖动。一次真正没有变化的升级，应尽量不产生这些副作用。

代价也存在：`groupName` 是业务键的一部分，因此改名会被处理成旧键消失、新键出现。如果未来其他对象长期引用分组身份，就需要重新评估是否引入稳定的来源标识。

## 5. 导入同步：来源与修改状态是两个维度

导入实体新增了两个字段：

```text
sourceImportId：对应哪一条元模型源导入
userModified：工程用户是否修改过这条框架管理行
```

跨工程克隆写入来源，同工程复制会清除来源，避免用户复制出的关系仍被误当成模板副本。编辑框架管理行时置位 `userModified`，目前没有自动复位机制。

下面是当前同步方法的行为，范围限于本次映射圈定的数据：

| 源行情况 | 工程行情况 | 行为 |
| --- | --- | --- |
| 存在 | 有配对，未标记用户修改 | 重算工程域期望值，有差异才更新 |
| 存在 | 有配对，已标记用户修改 | 跳过内容对齐 |
| 存在 | 没有配对 | 补插，并写入来源 |
| 源工程确认已不存在 | 仍有来源配对行 | 删除工程侧行 |
| 不适用 | 认领后仍无来源的行 | 保留 |

注意表里的删除规则：**`userModified` 当前保护的是内容更新分支，不是所有删除分支。** 在源行已经删除的路径里，代码没有再次按这个标记豁免目标行。因此不能把本实现概括成“用户改过的数据永远不会被升级删除”。

删除前还有一道范围检查：当前映射内找不到源行，不等于源工程里已经没有源行。实现会再查未配对的来源 ID；如果源行仍存在，只是宿主不在本轮映射里，就跳过删除。这防止把“本次没查到”误当成“已经不存在”。

## 6. 历史认领与用户删除，暴露了信息缺口

老工程在来源字段上线前已经存在，无法凭空知道每条导入的来历。当前做法是把宿主与内部引用归一化回元模型域，再比较目标、开关、可见性和别名；键一致就补写 `sourceImportId`。

这是一个实用的历史兼容策略，但内容一致不能证明历史来源。一条用户手工创建的关系，也可能恰好与模板默认值完全一致。当前认领键也不是全部持久化字段的完整快照。

因此，我会把它定义为“按等价内容推断来源”，不会把它描述成无歧义的历史追溯。若产品要求严格保留用户所有权，需要进一步引入认领预览、历史创建证据，或者只自动认领有充分证据的子集。

删除则是另一个信息缺口：

```text
用户删除了工程里的框架导入
→ 数据行消失，没有删除记录参与同步
→ 元模型源行仍在
→ 下次升级发现没有配对行
→ 重新补插
```

当前没有为这类删除建立墓碑记录，所以“删除后被补回”是算法可以推导出的行为。要记住用户的删除意图，需要额外保存类似 `(工程, 来源导入, 用户已删除)` 的状态，并定义模板再次调整时是否恢复。这是产品语义与存储模型一起增加的能力。

## 7. 什么时候需要三方合并

现有策略按整行决定“跟随源”或“保留用户值”。它成本较低，但粒度比较粗。

例如用户只改了别名，框架随后调整可见性。整行 `userModified=true` 会连新的可见性一起跳过。若产品希望两处修改自动合并，需要保存三个版本：

```text
base：上一次同步时的源值
local：工程当前值
remote：本次目标版源值
```

对单个字段，可以先采用下面的判断：

| 比较结果 | 候选动作 |
| --- | --- |
| local = base | 接受 remote |
| remote = base | 保留 local |
| local = remote | 无冲突 |
| 三者不同 | 进入冲突处理 |

这是后续设计选项，当前导入同步没有实现通用三方合并。引入它还要付出基线存储、字段语义、删除冲突和用户解释界面的成本；简单比较三个字符串并不足以覆盖引用对象消失等情况。

## 8. 技术负责人应该如何验收这类升级

本轮分组与导入同步挂在固定结构处理之后、动态实例处理之前。关联同步方法的异常直接向外传播，没有使用元素操作的逐条容错包装。

这表达了一个明确的实现意图：关联同步出错时，交给外层升级事务处理。它不能进一步证明所有元素操作都具有相同失败语义——主流程里仍有逐条容错与动态实例警告路径，也不能仅凭 Java 方法位置证明实际存储回滚已经验证。

我会把验收拆成几条能观察的约束：

1. 宿主、内部引用和外部引用分别映射正确。
2. 重复升级到同一目标版，不新增无意义记录。
3. 内容修改保护与源删除行为分别覆盖，不能共用一句“用户优先”。
4. 历史认领的歧义有明确处理口径。
5. 分组更新成功、导入同步失败等故障窗口经过真实存储验证。
6. 升级结果能解释“更新、保留、补回、删除”的原因。

仓库已有 `FrameworkFeatureConfigRebuildTest` 与 `ImportServiceImplSyncTest`，覆盖重映射、相同行不写入、用户修改、历史认领及标准库排除等场景。本文核对了测试源码，没有运行完整后端测试或数据库故障注入。

这个案例让我更看重平台的持续演进能力：第一次复制模板，通常不难；几年之后仍能解释哪些数据属于谁、为什么这次升级会改变它，才是长期维护中的核心工作。
