工程平台经常需要批量导入模型或任务，也需要把筛选结果导出为表格。数据稍大，接口就可能长时间没有响应。把处理放进线程池能释放请求线程，但用户仍然需要知道：任务是否开始、处理到哪里、失败了哪些行、结果在哪里。

SE-MBSE 的 Excel 导入导出框架将业务处理、过程支持与上下文分开，为这些问题提供了较清晰的组织方式。

## 三类对象各自负责什么

从当前调用关系看，Handler 负责业务数据及阶段钩子，Support 负责导入导出过程中的支持动作，Context 记录任务过程状态。

| 对象 | 在调用链中的作用 |
| --- | --- |
| Handler | 初始化、逐批业务处理、前后钩子、结束回调 |
| Support | 开始、写入、完成、错误等过程处理 |
| Context | 计数、失败信息、读写 Sheet 等执行状态 |

这种拆分让不同业务复用流程，也让导入与导出的任务界面有机会使用统一状态。具体状态是否持久化、是否支持进程重启恢复，还需要查看任务服务，不能只根据 Context 对象下结论。

## 分批处理让错误更容易定位

当前导入器通过读取监听器按批次交给业务 Handler。每批处理后记录总条数与错误数量，再将数据和错误列表交给 Support。

这比只有一个“导入失败”结果更适合用户：同一份表中可能只有少数行有问题，反馈应当让用户知道行号、字段和可修复原因。

批次大小也不是越大越好。大批次减少调用次数，但一次事务、对象集合和错误回传可能变得更重；小批次反馈更细，却可能增加数据库与任务更新成本。应根据行大小和业务处理成本测量，而不是只看文件体积。

## 异步是执行方式，不是业务语义

当前导入器和导出器都根据参数选择：提交给 executor，或者在当前线程直接执行同一套处理流程。这让执行逻辑能够复用。

但异步模式需要额外明确提交失败怎么办。例如执行器拒绝任务时，状态是否仍停留在“等待中”；任务执行期间进程退出，是否有可恢复的记录；用户重复点击，是否创建多个相同任务。

这些属于任务入口和持久状态的设计，不能通过把方法命名为 Async 自动解决。

## 导出的分页总数是某个时刻的观察

当前导出器先读取第一页取得 total 和分页信息，再按页继续取数。多 Sheet 版本对每个 Handler 依次执行，并累计预计数量。

如果导出期间源数据变化，第一页的总数与后续页面未必属于同一个快照。插入或删除还可能导致基于页码的结果漂移。

对于需要可重复结果的工程数据，可以考虑按版本导出、建立明确快照，或使用稳定排序与游标策略。是否需要这些措施，取决于导出的用途；工作台临时报表与正式交付清单，容忍度通常不同。

## finally 只是收尾位置，仍要检查收尾内容

当前流程在 finally 中调用 Handler 回调，并通过 Support 表达完成或异常。这个结构给资源释放提供了位置，但还应继续核对：文件流、Excel reader/writer、临时文件由谁真正关闭和删除，回调自身异常如何处理。

尤其多 Handler 场景，一个回调失败不应让后续资源永远得不到收尾。把“谁创建、谁释放”列成表，比只看有没有 finally 更可靠。

## 交付标准应包括失败文件

验证时，除了正常导出，还应准备空表、错误表头、部分行失败、分页过程中数据变化、任务提交被拒绝，以及读写异常等场景。

用户最终需要一个可解释的任务结果。处理成功的数量、失败的原因和可重试范围，应当相互一致。把这些状态设计好，异步化才能改善体验，而不只是把等待从接口转移到一个进度条。
