工程工具集成中，接口返回了文本，并不意味着已经拿到了可用资源。它可能是登录页、代理错误页，也可能是合法 XML，却没有预期的 RDF 数据。

SE-MBSE 的 OSLC 解析层把 Jena Model 的读取集中到一个工具中，先建立输入边界，再由上层解析具体资源。这种拆分让外部协议问题更容易被定位。

## 三类失败不应该合成一种错误

当前读取流程至少区分三种情况：输入为空；RDF/XML 读取时发生异常；读取后模型为空。

这三种情况对应不同排查方向：

| 现象 | 优先检查 |
| --- | --- |
| 没有内容 | 请求与返回值处理是否完整 |
| 格式读取失败 | 是否拿到 HTML、错误页或损坏文本 |
| 没有三元组 | 返回内容是否真正表达 RDF 数据 |

如果统一处理为“解析失败”，调用方就不得不反复下载原始内容，才能判断问题发生在哪一层。

当前工具还附带有限长度的文本预览与开头若干 Unicode 码点，帮助识别不可见字符等输入问题。预览长度有限不等于已经脱敏，公开日志仍需按数据敏感程度约束输出。

## RDF 资源不是普通 JSON 对象

RDF 用主语、谓语、宾语构成语句。Jena Model 提供面向这些关系的访问接口，因此解析重点是资源类型、属性 URI 与节点类型，而不是仅按文本标签的表面结构取值。[Jena RDF API 教程](https://jena.apache.org/tutorials/rdf_api.html)

以下三元组仅用于解释，不来自真实工程：

```text
<urn:demo:requirement:42>  <urn:demo:title>  "温度监测"
```

资源的身份是 URI，标题是属性值。不能因为两个标题一样，就把两个资源当作同一个对象。

## 节点类型决定如何读取值

当前 `nodeValue` 分别处理 URI 资源、匿名节点和字面量：URI 返回地址，匿名节点返回内部标签，字面量返回词法形式。

这个方法方便统一取字符串，但也会弱化一部分语义。字面量可能带语言或数据类型；只取词法形式时，这些信息没有进入返回值。匿名节点的标签也不应直接视为跨文档稳定的业务 ID。

如果后续业务需要区分语言、单位或数值类型，应该在上层保留相应结构，而不是把所有节点过早压成字符串。

## 取第一个值，需要有协议依据

当前工具既提供全部值查询，也提供 `firstValue` 和按类型查找第一个主语的方法。

“只要第一个”是一种明确的选择，适合上层契约规定单值的场景。若资源可能有多个相同属性，顺手取第一个可能隐藏了数据异常；若有多个同类型资源，也不能未经约定就认为遍历中的首项是目标。

因此，解析层应将读取便利与业务约束区分开：基础工具负责取值，具体解析器负责判断是否唯一、是否必需以及缺失时如何处理。

## Model 可读，不代表业务数据完整

基础模型成功构造后，仍需要验证目标资源存在、必需属性齐全、引用地址可识别等条件。反过来，基础读取层不必承担所有工具的业务规则，否则它会逐渐变成一个复杂的分支集合。

可用一组小型样例建立回归：空字符串、HTML 文本、没有三元组的输入、多资源、多值属性、匿名节点和带语言的字面量。样例应使用独立的虚构 URI，便于公开复现。

外部集成的稳定性，依赖的是每一层都给出清楚的成功与失败含义。从“收到文本”到“得到模型”，再到“得到有效业务资源”，这些阶段不应该被压成同一个解析函数。
