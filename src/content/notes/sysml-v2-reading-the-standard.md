做建模平台时，很容易从界面反推语言：树上有哪些节点，工具箱里有哪些图形，属性窗需要几个输入框。

这种方式能很快做出一个编辑器，却不一定能得到一致的模型。两个方框能连上线，不代表那条线具有正确的领域含义；文本能解析，也不代表模型满足工程约束。

我希望把 SysML v2 的阅读顺序反过来：先回答模型表达了什么，再讨论怎样显示、存储和操作它。

这组文章是结合建模平台工作形成的个人解读，不是 OMG 官方教程，也不把标准能力等同于 SE-MBSE 已实现的能力。

## 1. 先固定文档版本

截至 2026 年 10 月 20 日，OMG 官方目录提供的正式版本是 SysML 2.0、KerML 1.0 和 Systems Modeling API and Services 1.0；当前 PDF 文档号分别为 `formal/2026-03-02`、`formal/2026-03-01`、`formal/2026-03-04`，封面日期均为 2026 年 3 月。SysML 2.0 的正式版本历史记录仍标为 2025 年 9 月。[SysML 官方目录](https://www.omg.org/spec/SysML/2.0)、[KerML 官方目录](https://www.omg.org/spec/KerML/1.0)、[API 官方目录](https://www.omg.org/spec/SystemsModelingAPI/1.0)

需要同时记录“规范版本”和“文档修订”，不能看到 PDF 更新就把语言版本称为 SysML 2.1。搜索结果里的 Beta 文档和旧示例也不能自动代替当前正式文档。

对团队而言，我建议在设计记录里保存四个字段：规范名称、版本、文档号、相关条款。文件哈希可以再补一个。这样半年后讨论某个规则时，大家知道当时依据的是哪份材料。

## 2. 把标准体系看成几种不同的问题

SysML 以 KerML 为基础，并同时提供文本与图形表示；标准 API 则承担模型访问和工具互操作方面的职责。[OMG SysML v2 概览](https://www.omg.org/sysml/sysmlv2/)

下面是我实际阅读时使用的分工表。它是一条工作路线，不是标准要求的学习顺序。

| 要回答的问题 | 优先查哪里 | 我通常要找的证据 |
| --- | --- | --- |
| 这种建模概念该怎么用 | SysML 第 7 章 | 使用规则、上下文与最小示例 |
| 文本与图形如何表达 | SysML 第 8 章具体语法 | 记号和对应结构 |
| 模型中到底有什么对象和关系 | SysML 第 8 章抽象语法 | 元类、属性、派生属性和约束 |
| 这个概念为什么有这种含义 | SysML 语义章节及 KerML | 特化、特征、求值等基础 |
| 默认含义和量纲从哪里来 | 规范模型库与第 9 章 | 基础类型、隐式关系和库引用 |
| 如何通过服务读取某一版本 | Systems Modeling API | 身份、提交、版本与导航接口 |

章节入口可在 [SysML 正式规范目录](https://www.omg.org/spec/SysML/2.0/Language/PDF#page=10)核对。

这张表最有用的时候，是研发把问题统称为“解析器问题”。缺少一个分号属于语法问题，名字指向错误的对象属于解析和语义问题，图上显示错误的标签可能属于呈现问题。它们需要不同的修复位置。

## 3. 用一个小系统建立语义锚点

以下是本文原创的 SysML 文本示例。代码块使用普通文本展示，便于关注语言本身：

```text
package CoolingStructure {
    part def Pump;

    part def CoolingUnit {
        part primary : Pump[1];
        part standby : Pump[1];
    }
}
```

我们想表达的是一个冷却单元有主泵和备用泵两个角色。

接下来可以画出两张图：

- 结构视图展示冷却单元和两个泵角色；
- 维护视图只展示泵以及维护人员关心的信息。

两张图使用同一语义模型，还是各自复制一套泵对象，是平台架构必须作出的决定。对于这个例子，我会让不同呈现引用同一个语义元素，否则主泵改名时就需要猜测另一张图上哪个对象与它对应。

这种对象复用属于我的实现建议。不能据此声称标准要求数据库必须采用某种表结构，或要求前端必须采用某种图形引擎。

## 4. 四个层次的“正确”需要分别证明

围绕上面的模型，可以设计四组问题：

| 层次 | 例子 | 检查通过说明什么 |
| --- | --- | --- |
| 文本可解析 | `part` 声明和花括号是否合法 | 能建立相应语法结构 |
| 模型语义一致 | `Pump` 能否解析，角色是否使用正确类型 | 模型关系符合相应规则 |
| 工程约束成立 | 一台泵失效后，剩余能力是否足够 | 在规定条件下满足设计目标 |
| 工程证据充分 | 能力数据来自哪个试验、哪版设备 | 结论可追溯、可复核 |

这四层没有自动跳跃关系。

文本通过解析，不会自动给出泵的流量；填了流量参数，不会自动提供失效后的性能证据；有一张“验证通过”的图，也不证明结果针对当前版本。

因此我更愿意让平台显示具体检查项，而不是只有一个不加解释的“模型校验通过”。

## 5. 抽象语法不是数据库设计图

阅读元模型时，一个常见冲动是把每个元类映射成一张表，把每条关系映射成一个外键，然后认为标准适配工作已经完成。

我会先追问一个更小的问题：当用户给 `primary` 指定 `Pump` 类型时，系统如何证明这个引用存在、可见且类别正确？

如果只在字段里保存 `"Pump"`，两个包中出现同名定义时怎么办？如果复制一份定义的属性到 Usage，原定义变化时怎么办？如果把继承后可见的所有特征都保存成“直接拥有”，导出时还能区分它们的来源吗？

这些问题说明，持久化层需要保留的首先是语义身份和关系，而不只是最终界面上的文字。

合理实现可以采用关系数据库、图数据库或其他存储。关键是能否恢复并检验语言要求的结构，而不是物理表名是否与元类名称相同。

## 6. 模型库应进入可复现边界

假设同一份文本在开发机上能解析，在另一台机器上却找不到类型。除了语法版本，还应该检查模型库、导入范围和名字解析上下文。

我的项目配置建议是把“语言文档版本、模型库版本、解析器版本”一起记录。模型库升级后，不仅运行语法测试，还要检查：

- 已有引用是否仍能解析；
- 隐式推导结果是否改变；
- 导出再导入后身份和关系是否保持；
- 同名成员是否出现新的歧义。

这里的可复现目标很具体：同一份模型，配合同一组依赖，应得到可解释的一致结果。仅保存一个 `.sysml` 文件名往往不足以追踪环境差异。

## 7. 对 AI 建模尤其重要的一条边界

一个助手完全可能生成语法漂亮、工程含义却不完整的模型。例如它创建了两台泵，就说“已完成冗余设计”。

我会要求它把结论拆开：

1. 已建立哪些结构元素和关系；
2. 已表达哪些约束；
3. 哪些约束已求值；
4. 哪些结论仍缺少参数或验证证据。

这不是增加话术，而是让工具结果与可证明的事实对应。AI 可以帮助构造和检查模型，但不能把一段说明文字变成标准意义上的证据。

## 8. 怎样读一个具体条款

拿到一个陌生概念，我通常按下面的顺序处理：

1. 用自己的话写一句“它要表达什么”；
2. 写一个最小正例；
3. 写一个只改动一个条件的反例；
4. 回到抽象语法和约束解释差异；
5. 再决定编辑器如何提供操作、错误如何反馈。
